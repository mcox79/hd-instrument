# Cross-module interface: how modules share an entity/concept vocabulary to reason across domains

Date 2026-07-15. Re-dispatch (prior attempt died on a transient API connection error). Method: 3 parallel Sonnet lit-scan sub-agents (biology-led: TEM structure/content factorization + analogical mapping; best-in-class: entity resolution for scientific KBs; best-in-class: multi-domain KG integration architecture), synthesized here. Generic search terms only, no substrate-specifics off-platform, per query-privacy discipline.

Context this answers: we are about to lock a module-registry schema for INGESTED conjunction modules (drug-drug synergy, gene-gene epistasis, chemistry nonadditivity). The open problem is how a gene in an epistasis module, the same gene as a drug TARGET in a synergy module, and a chemical in a nonadditivity module all refer to "the same thing" without naive KB-merge entity-linking's famous precision collapse.

## HEADLINE

**Build ONE thin canonical-ID entity-identity registry (the hub) that every module (spoke) normalizes its local entities against once; keep each module's own relational/bind machinery fully separate and domain-specific underneath. Cross-module reasoning is IDENTITY-ANCHORED GRAPH TRAVERSAL across the registry, not a merged joint embedding space.** This is simultaneously (a) the brain's own answer (ATL hub-and-spoke: one shared, amodal identity space that domain-specific "spokes" bind their own content onto — NOT a single merged representation) and (b) the field's own best-practice answer for exactly this problem (NCATS Biomedical Data Translator's Babel/Node-Normalization + Biolink Model architecture, which is a live, multiply-corroborated production system solving this precise cross-KB gene/drug/chemical identity problem at scale). The naive ~50%-ish entity-linking precision ceiling reported for general heterogeneous-KB fusion **substantially dissolves** for our modules specifically because drug/gene/chemical datasets carry maintained canonical IDs (HGNC/Entrez/UniProt/PubChem CID/InChIKey/ChEMBL/DrugBank/NSC) with dedicated crosswalk infrastructure (UniChem, MyGene.info, Bioregistry) already engineered around the narrow residual failure modes (stale IDs, splits/merges, salt-form/stereo variants, coverage gaps) — those failure modes are ~5-15%-scale maintenance problems, not ~50%-scale ambiguity.

## Brain answer (Q1 + Q2)

**One shared identity hub, not per-domain codes linked post-hoc, and NOT a single merged content representation.** Hub-and-spoke (Rogers 2004; Patterson, Nestor & Rogers 2007 *Nat Rev Neurosci*; Lambon Ralph, Jefferies, Patterson & Rogers 2017 *Nat Rev Neurosci*) is the dominant account: bilateral ventrolateral anterior temporal lobe (ATL) computes a transmodal SIMILARITY/IDENTITY space from modality-specific spokes; semantic-dementia lesion evidence shows ATL damage causes pan-category, cross-modal degradation (not modality-specific), the classic signature of a genuinely shared convergence computation rather than parallel special-purpose systems (already established in our prior notes `research_brain_grounding_spoke_building_canonical_reference_2026-07-14.md` and `research_brain_grounding_flexibility_open_spoke_registry_2026-07-14.md` — this drill extends those with the structure-transfer question specifically). Content-agnostic bind = convergence-divergence zones (Damasio 1989; Meyer & Damasio 2009 *Trends Neurosci*): a CDZ does not store content, it stores the CONJUNCTION (hub identity <-> spoke content) via Hebbian co-activation and reconstructs by divergent re-activation — the same operation regardless of which spoke.

**Structure-transfer is a DIFFERENT, adjacent mechanism — and it is important not to conflate the two.** The Tolman-Eichenbaum Machine (Whittington, Behrens et al., *Cell* 2020; "Binding in hippocampal-entorhinal circuits enables compositionality in cognitive maps," NeurIPS 2024, arXiv:2406.18808) factorizes a RELATIONAL/STRUCTURAL code (entorhinal, content-free, e.g. transition-graph structure) from a CONTENT code (lateral entorhinal, sensory-specific), bound together conjunctively at the hippocampus. Grid-cell-like hexagonal-symmetry signatures for this SAME structural code have been found reused across spatial navigation, 2D conceptual/feature spaces (Constantinescu, O'Reilly, Behrens, *Science* 2016), and 2D social hierarchies (Park, Miller, Boorman et al., *Nat Neurosci* 2021) — direct, quantitative (RSA/periodicity) evidence that ONE structural scaffold generalizes when the SAME relational structure recurs across different content domains, with content simply swapped in via binding. Independent convergent evidence: mouse mPFC/hippocampus task-structure generalization (*Nat Neurosci* 2022) and macaque premotor near-orthogonal schema-vs-task-content subspaces (*Nat Commun* 2026) — three separate literatures agree that "structure reused, content swapped via a binding/orthogonal-subspace operation" is the general strategy, not "learn everything fresh per domain."

**Which applies to us? Mostly the ATL hub-and-spoke picture, not TEM structure-reuse — and that distinction is itself the useful finding.** TEM's structure-transfer condition is: the SAME relational/transition structure recurs, only the content changes (e.g. the same maze topology in a new room). Our modules do NOT share the same relation type — gene-gene epistasis, drug-drug synergy, and chemistry nonadditivity are three genuinely DIFFERENT relational structures over (partly) the same entities, not one structure with swapped content. That is the ATL hub-and-spoke regime: one shared IDENTITY space, with each spoke/module free to carry its own domain-specific relational code on top. Gentner's structure-mapping theory (SMT) and its computational lineage (SME; LISA/DORA — Hummel & Holyoak 2003; Doumas & Hummel) describe the case of aligning two ALREADY independently-structured domains post-hoc via role-binding (not synchrony-of-one-shared-code) — this is the closer analogy for what happens when a query crosses from the epistasis module's relational vocabulary into the synergy module's, since those two relational structures were built independently and only share entities, not relation-shape. (Honest open seam per the lit-scan: the field has not unified within-family TEM-style structure-reuse and cross-family Gentner-style post-hoc alignment into one mechanism — flag as unresolved, not something this drill is failing to find.)

## Best-in-class entity linking (Q3)

**Two clean regimes, confirmed convergently across all three lit-scans.** (1) No shared ID (general/heterogeneous KB fusion via string-matching, cross-lingual/cross-source entity alignment, OAEI-style ontology matching): naive surface-matching recall/precision sits roughly in a 50-77% band depending on candidate-set restriction (candidate-restricted surface-matching benchmark: oracle recall 77% dropping to 50% when candidates capped at 100); Knowledge Vault (Dong et al., KDD 2014) explicitly motivates multi-signal fusion because single naive-extractor/linker precision is mediocre; state-of-the-art embedding-based KG entity-alignment methods (MTransE, JAPE, GCN-Align, OntoEA) report "high precision but modest recall," still below an exact join. **The specific "~51%" figure was not found verbatim in any single citable source this session** — it is consistent with, but not independently confirmed as, this naive-surface-matching/no-shared-ID regime; flag as approximately-right-order-of-magnitude, not a precisely sourced statistic, and don't cite it as a hard number downstream without further sourcing.

(2) Shared canonical ID exists (our actual case — genes/drugs/chemicals): the problem is CATEGORICALLY different — reframed from probabilistic "is this the same entity" into deterministic "which crosswalk-table version resolves ID-A to ID-B," maintained by dedicated infrastructure: **UniChem** (EBI; Chambers et al. 2013, *J. Cheminformatics*) keys chemicals on InChI/InChIKey with explicit salt/connectivity/stereochemistry-layer handling; **MyGene.info** resolves Entrez/Ensembl/HGNC gene IDs to each other; **Bioregistry** (*Sci Data* 2022) consolidates ~2,100 namespace entries (successor to Bio2RDF/MIRIAM/identifiers.org) for unambiguous ID-system reference; **PubChem Identifier Exchange** does the CID/SID/InChIKey/SMILES crosswalk natively. Documented residual failure modes are narrow and actively engineered around, not ~50%-scale: stale/withdrawn gene symbols (e.g. HGNC "ACPT" -> "ACP4"), one-to-many gene splits/merges across annotation releases, version/release skew (mappings resolved only within a specific Ensembl/Entrez/HGNC release), coverage gaps between specific DB pairs (ChEMBL lacks direct PubChem SID links except via BioAssay records, ~450K record shortfall documented), and occasional curation errors (a documented case: an erroneous PubChem CID for "BMS 275291," corrected via UniChem/ChEMBL cross-check). **Answer: yes, the naive entity-linking precision problem largely dissolves for canonical-ID-carrying scientific modules — conditional on the pipeline actually using a maintained crosswalk service (UniChem/MyGene.info/Bioregistry) rather than name-string matching, and on ID versions being kept consistent across joined datasets.** If a dataset only carries free-text names/aliases (no ID), it reverts fully to regime (1).

## Best-in-class KG integration architecture (Q3/Q4, cross-module reasoning)

The **NCATS Biomedical Data Translator** is a live, production, multiply-corroborated instance of exactly our target architecture and is the strongest single piece of evidence in this drill. Its identity layer, **Babel** (github.com/NCATSTranslator/Babel), ingests IDs from hundreds of sources and merges them into **cliques** (sets of IDs asserted to denote the same real-world entity, one per semantic type: gene, chemical, disease...), each clique carrying a designated **clique leader** (canonical/preferred ID chosen via a deterministic, ranked prefix-priority list per entity type — not ML-based resolution). **Node Normalization (NodeNorm)** exposes this as an HTTP service: any Knowledge Provider (KP, = our "module") normalizes its LOCAL entity IDs against NodeNorm ONCE, and thereafter speaks in canonical clique-leader IDs — so KPs never need pairwise ID-mapping agreements with each other. This is architecturally the classical Master Data Management "thin master registry" pattern (a minimal index mapping unique entities to source records, contrasted with a heavier "golden record" full merge) applied to biomedical identifiers. Identity (Babel/NodeNorm) and schema/relation-typing (the separate **Biolink Model** upper ontology) are kept as **separate hub services** — don't conflate identity-resolution with relation-schema-alignment into one mechanism.

Cross-domain composition in the flagship reasoning agent (**ARAX**, Bioinformatics 2023) is literal graph traversal, not embedding composition or meta-path algebra: a 5-stage pipeline (Expand -> Overlay -> Filter -> Resultify -> Rank) fans a query graph out live across KPs, joining edges from different KPs PURELY because their endpoint node IDs are already Babel-normalized to the same clique leader — no semantic translation of one module's relation type into another's occurs; each module's native relation vocabulary is preserved and only typed against a shared upper ontology for filtering. KG-embedding composition and meta-path-based reasoning exist in the wider heterogeneous-information-network literature but as a downstream RANKING/plausibility layer over an already-identity-joined graph, not as the join mechanism itself — evidence against over-investing in embedding-composition machinery before the identity hub is solid.

Known failure modes for this pattern (medRxiv 2026 "Beyond Identifier Matching" taxonomy, abstract-level only, full text inaccessible this session; corroborated independently by BridgeDb/orthogene/SSSOM tooling literature): peer over-merging (two related-but-distinct entities incorrectly cliqued, e.g. paralogs), parent-child collapse (drug class conflated with a specific drug), lexical false positives, granularity asymmetry across source DBs, and version/scope drift (silent reproducibility failure — same ID, different underlying referent across releases). Mitigations already field-standard: version-stamp every equivalence claim against source-DB release; record equivalence STRENGTH as a typed relation (SSSOM's exact/close/broad-match, not a flat boolean); treat non-1:1 mappings as first-class and exposed, not silently resolved (BridgeDb/orthogene pattern).

## RANKED recommendation for our cross-module interface

**Rank 1 (recommended): hybrid, hub-identity + spoke-relation.** One thin canonical-ID entity registry (hub) — a VSA hypervector code assigned per canonical ID (one code per Babel-style clique), generated once and shared read-only across all modules. Each module keeps its own INTERNAL relational/bind machinery fully separate (its own bind operator, its own relation-type vocabulary, its own conjunction-module reasoning) and only NORMALIZES its local entities against the hub registry at ingest time (module writes `local_entity -> canonical_id -> hub_code`, once, not pairwise against every other module). This is simultaneously the brain-aligned answer (ATL hub-and-spoke: shared identity, per-spoke content/relational code) and the pragmatic answer (mirrors Babel/NodeNorm + Biolink, a validated production pattern for this exact entity type).

Rank 2 (rejected as primary, viable as a later optimization): pure unified single global graph merging all modules' triples into one store (Hetionet/PrimeKG/SPOKE-style). Workable but couples modules tightly, forces one relation-schema, loses each module's domain-specific bind machinery, and isn't necessary for correctness — the biomedical field itself increasingly separates identity-merge from schema-merge (Babel vs Biolink) rather than doing one flat merge.

Rank 3 (rejected as primary): learned-embedding cross-module entity alignment (MTransE/JAPE/GCN-Align-style) with no canonical-ID join. This is the right tool ONLY when no shared identifier exists (general KG fusion, cross-lingual KBs) — our modules DO carry canonical IDs, so this is strictly dominated by an ID-join per the field's own revealed-preference pattern (alignment-embedding research energy concentrates in domains lacking shared IDs; ID-carrying domains build crosswalk infrastructure instead).

**Specific ID systems to key on:** genes -> HGNC ID/symbol (primary) + NCBI Entrez Gene ID (secondary, noted more version-stable) + Ensembl Gene ID, cross-mapped via MyGene.info; proteins -> UniProt accession (for gene-as-drug-target cases, since drug-target edges are usually protein-level); chemicals/compounds -> InChIKey (primary structure-based canonical key) + PubChem CID, cross-mapped via UniChem; drugs -> DrugBank ID + NCI NSC number (for NCI-ALMANAC-sourced data specifically), cross-mapped via UniChem/DrugBank's own salt-vs-active-moiety schema. Use Bioregistry/identifiers.org as the namespace-curation layer so every module's ID references are unambiguous about WHICH ID system they mean.

**How the bind composes a cross-module conjunction:** each module M owns its own `bind_M(hub_code(id_A), hub_code(id_B), relation_type_M) -> conjunction_vector_M`, using entity codes drawn from the SHARED hub registry but a relational/bind operator that is fully module-local (this is the honest brain distinction above: modules don't share relational STRUCTURE, only entity IDENTITY). A cross-module query is a CHAINED unbind across the identity join, mirroring ARAX's Expand-across-KPs pattern in bind/unbind terms: `unbind_{M1}(hub_code(gene_X)) -> partner code -> hub-registry lookup confirms partner is also indexed in M2 (e.g. gene_X's canonical ID also resolves, via UniProt, to a drug target in the synergy module) -> bind_{M2}(hub_code(gene_X_as_target), hub_code(drug_Y), relation_type_M2) -> conjunction_vector_M2`. The join step is pure identity-equality lookup in the hub registry (cheap, deterministic, no learned alignment); each module's bind/conjunction math never needs to know the other module's relation vocabulary exists. No merged joint bind space across modules is required or recommended.

## Cheap decisive test / how to stress-test with module #2

Build the hub registry + module #1 (e.g. gene-gene epistasis, canonical IDs = HGNC) first. Then register a genuinely SECOND module (e.g. chemistry QSAR nonadditivity or drug-drug synergy, canonical IDs = InChIKey/DrugBank, sharing at least a handful of entities with module #1 via a real cross-reference, e.g. genes that are also drug targets via UniProt-DrugBank target links) against the SAME hub registry, with ZERO changes to module #1's code path, and run a 2-hop cross-module query (module-1 edge -> hub identity join -> module-2 edge) end to end.

**HARD-PASS:** (i) module #1's held-out within-module performance is unchanged (+/- noise floor) after module #2 is registered — the hub is genuinely additive, no rewrite needed; (ii) the 2-hop cross-module query retrieves the correct joined entity/relation pair at above-chance precision using ONLY canonical-ID equality (no learned alignment step); (iii) a deliberately introduced ID-version mismatch (e.g. a stale HGNC symbol in one module's local entity table) is caught/flagged by the hub rather than silently mis-joining.

**HARD-FAIL:** (i) registering module #2 measurably degrades module #1's performance (interference — contradicts the additive-hub claim, means real coupling exists and the "modules stay independent" architecture doesn't hold); (ii) the cross-module 2-hop query requires anything beyond canonical-ID equality to get a correct join (e.g. needs a learned similarity threshold) — meaning the "51% dissolves for canonical-ID data" claim was too optimistic for this entity-type pair and a fallback fuzzy-matching layer is actually required; (iii) the stale-ID mismatch silently produces a wrong join with no detectable signature — meaning the hub needs SSSOM-style typed/versioned equivalence tracking before it's safe to trust, not a flat identity table.

## Substrate-product implications

Do not lock a module schema that merges modules into one graph or invents a bespoke pairwise entity-linking step per module pair. Lock instead: (1) one canonical-ID hub registry service, versioned per source-DB release, with clique-leader selection via a deterministic prefix-priority rule per entity type (Babel-style); (2) a required "normalize against hub" step at every module's ingest boundary, never at query time and never pairwise; (3) each module keeps 100% of its own relation-schema and bind operator, contributing nothing to a shared relational schema (only Biolink-style TYPE tags for filtering, if even that); (4) cross-module reasoning implemented as identity-anchored bind/unbind chaining (traversal), with embedding-based cross-module alignment explicitly deferred/rejected as unnecessary machinery given canonical IDs are present; (5) equivalence claims in the hub carry a typed strength (exact/close/broad, SSSOM-style) and a source-release version stamp from day one, not bolted on later — this is the single most load-bearing engineering lesson from the failure-mode literature and is cheap to build in now vs expensive to retrofit.

## Falsifiable predictions (HARD-PASS / HARD-FAIL) — summary

- P1: canonical-ID hub join precision for our modules is materially above the naive ~50-77% string-matching band (near-deterministic, residual failure <15%). HARD-FAIL: observed cross-module join precision on a held-out audited sample is NOT meaningfully better than naive string/name matching for the SAME entity pairs — would mean our specific datasets' ID hygiene is worse than the general bioinformatics literature implies, and a fuzzy-matching fallback layer is required after all.
- P2: hub registry is additive across modules (see cheap decisive test above) — a module can be added without touching another module's code or degrading its performance.
- P3: cross-module 2-hop composition works via identity-anchored traversal alone, without needing a learned cross-module similarity/alignment step. HARD-FAIL: correct cross-module joins require a learned alignment component beyond ID-equality, meaning our entity overlap across modules is sparser/noisier than the ARAX/Translator precedent and embedding-based alignment (Rank 3, above) needs to be reintroduced as a fallback.
