## HEADLINE

**The foundation is not one graph at one density — it is a two-tier architecture, exactly mirroring the brain-side hub-and-spoke finding delivered the same day: a DENSE SHARED RELATIONAL CORE (universal — every concept gets identity/definition + taxonomy + a minimum spanning set of relation TYPES) plus an OPEN REGISTRY of MODULAR DOMAIN GROUNDINGS (physical/chemical/geographic/biological/etc.) that attach onto core entities without ever requiring the core to be rebuilt.** This is not a new invention for the KG side — it is the direct structural analog of what the brain-grounding note found bio-evidenced (CDZ hub + spoke registry, admission by contingency-test not channel-taxonomy) applied to symbolic/relational knowledge instead of sensory grounding, and it resolves the earlier draft's "how big should the graph be" framing into a cleaner, more actionable question: **how big should the CORE be, and what is the ADMISSION TEST for a MODULE.**

**Density target reframed** (the sharpest correction from the coordinator's refinement): raw avg-degree/k-core numbers (still reported below, still useful as a coarse proxy) are NOT the target metric. The real target is **per-concept relation-TYPE coverage**: does this concept have at least one edge in each of the ~5-8 characterizing relation-type buckets that apply to its ontological category (taxonomic, property/attribute, part-whole, functional/use, causal/event, spatial-if-applicable, social/agentive-if-applicable)? Our own diagnosed 59%-degree-1 tail is pathological NOT because the count is low, but because a degree-1 node is by construction characterized along **at most one** relation-type axis (almost always a single IsA-parent) — it has no property, no use, no part-whole, no causal edge at all. **"Too dense" is redundant same-bucket edges** (50 near-duplicate synonym/IsA-parent edges is not better characterization, it's the same axis repeated) — this is a genuinely different failure mode from sparsity and should be measured/capped separately.

**Multilingual reframed as concept-centric, not language-centric**: one language-independent concept node (a Wikidata-QID-style or BabelNet-synset-style identity) carries multilingual LABELS as an attribute, not as separate per-language nodes — this is already the proven design in both Wikidata and BabelNet, not a new proposal. A small number of genuinely non-cross-lingual, culture-specific concepts (untranslatable-word cases: "hygge," "saudade," "ubuntu"-the-philosophy, culture-specific rituals/institutions) DO get their own dedicated node, exactly as BabelNet's own merge algorithm already handles lexical gaps. Beyond-brain/superhuman coverage is partly THIS: drawing concepts (not just labels) from many languages/cultures/technical domains that no single human population's commonsense vocabulary would surface.

**Modularity reframed as an open registry, directly mirroring the brain-side note's admission test**: a MODULE (PubChem, Materials-Project/periodic-table data, GeoNames, UMLS, a future module not yet identified) is admitted by passing a generic test — not by hand-integrating a bespoke pipeline. Cross-module interconnection happens **through shared core entities** (a "diamond" node carries hardness/electronic-structure from a materials module, molecular formula from a chemistry module, and gem/jewelry-use from the commonsense core, all bound to the SAME core entity), not by exhaustive module-to-module linking — adding a module only requires (a) anchoring its entities to core entities and (b) reconciling any attribute collisions where two modules assert something about the SAME core entity. This is the direct, load-bearing cost of modularity and is addressed concretely in Section 5.

## 0. Architecture: CORE + MODULE REGISTRY (the structural spine of this spec)

### 0a. The CORE — what every concept gets, resource mapping

The core is the UNIVERSAL layer: every concept, regardless of domain, gets an identity, a taxonomic placement, a definitional gloss, and a minimum spanning set of general-purpose relation types (property, part-whole, functional/use, causal, spatial where applicable). This is domain-agnostic by design — it is what CSKG already targets, and what general-purpose lexical/encyclopedic resources supply.

**Resources that supply the CORE** (general-purpose, apply to every concept type, already-precedented merge target):
- **Wikidata (full, not just Wikidata-CS subset)** — universal identity backbone (QIDs), broad taxonomic/factual coverage, CC0, 122.4M items.
- **ConceptNet** — commonsense relational core (already in CSKG): property/use/part/causal/spatial edges.
- **ATOMIC/ATOMIC2020** — general social/event-causal commonsense (already in CSKG): this is CORE, not a domain module, because it characterizes essentially any agentive/event concept, not a technical vertical.
- **WordNet** — taxonomic backbone (synsets, hypernymy), already in CSKG.
- **Wiktionary/Wiktextract** — lexical-morphological layer (etymology, inflection, pronunciation, multilingual senses) — NOT currently in CSKG, a genuine core-layer gap identified in Section 1 below.
- **YAGO 4.5** — clean, logically-consistent taxonomy cross-check (schema.org + curated Wikidata slice) — a core-layer QUALITY tool (constraint-checking), not new content per se.
- **BabelNet** — the multilingual-LABEL layer for the core (see Section 3) — attaches multilingual labels to core concepts, not new module content.
- **FrameNet/Roget/VerbNet** — lexical-semantic/argument-structure core support (Roget/FrameNet already in CSKG; VerbNet not yet, a minor core-layer addition).

### 0b. MODULES — domain groundings that attach onto core entities

A module supplies domain-specific, typically MEASURED, attribute/relation content that only applies to a subset of core entities (chemical substances, geographic places, biomedical concepts, materials). Modules are NOT part of the universal core — a concept with no chemistry module attachment (e.g. "friendship") is not thereby "under-characterized" by core standards; it simply has no chemistry-module attachment because none applies.

**Resources that supply MODULES** (domain-specific, attach to a subset of core entities via entity-anchoring, per Section 5):
- **PubChem** — chemistry module (molecular formula, experimental physical/chemical properties) for substance-type core entities.
- **Periodic-table reference data / Materials Project** — materials/physical-properties module (atomic mass, electronegativity, hardness, melting point, crystal structure) for element/material-type core entities — already the Phase-1 buildable cell design in `research_grounding_foundation_build_plan_2026-07-13.md`; this spec confirms it is architecturally a MODULE, not core.
- **USDA FoodData Central** — nutritional/food-composition module for edible-substance core entities.
- **GeoNames** — geographic module (coordinates, feature type, population, elevation) for place-type core entities.
- **UMLS Metathesaurus** — biomedical module (clinical concepts, 78M relationships) for medical-concept core entities.
- **Gene Ontology / SNOMED CT** — genetic-function / clinical-terminology modules, narrower verticals within the biomedical space.
- **YCB object set / CLAMP haptic dataset** — small, high-precision physical-property/haptic modules for common-object core entities (already flagged in the 07-13 note as validation-scale, not bulk).

**Explicitly NOT modules, correctly reclassified as CORE**: ATOMIC (general event/social commonsense applies broadly, not to a narrow domain subset) and Wiktionary (lexical properties apply to essentially every concept that has a name, not a domain subset) — this is a genuine correction from the first-pass draft, which had implicitly treated the resource landscape as one flat list.

**Cyc/OpenCyc/NELL**: neither core nor a live module — Cyc's hand-curated FOL/microtheories are a conceptual reference for what a hand-curated core WOULD look like (worth citing as a design ideal for core consistency-checking, see Section 5's YAGO4-constraint discussion) but not itself ingestible (abandoned/proprietary); NELL is stale/noisy and not recommended for either tier without heavy re-filtering.

## 1. Density target — per-concept characterization, not raw node-count or max-edges

**The corrected target metric**: define a small, fixed set of characterizing relation-type BUCKETS applicable to a concept's ontological category — a concrete, workable starting set:

| Bucket | Example relations | Applies to |
|---|---|---|
| Taxonomic | IsA / instance-of / subclass-of | every concept |
| Property/attribute | HasProperty / MayHaveProperty | every concept |
| Part-whole | PartOf / HasA | composite/physical concepts |
| Functional/use | UsedFor / CapableOf | artifacts, tools, substances |
| Causal/event | Causes / MotivatedByGoal / xEffect-class | events, actions, agentive concepts |
| Spatial | AtLocation / LocatedNear | physical/place concepts |
| Social/agentive | xWant / xIntent / xReact-class | agents, social events |

**Concrete per-concept target: a concept is "characterized enough" when it has at least one edge in >= 4-5 of the buckets that apply to its ontological category** (a concept category itself determines which buckets are applicable — "friendship" doesn't need a spatial bucket, "Paris" does). This directly operationalizes the ~5-20-edges-spanning-key-types framing from the coordinator's refinement: the floor is not a raw edge count, it is TYPE DIVERSITY, with a soft cap of roughly 1-3 edges per bucket (more than that within a single bucket is measured as REDUNDANCY, not added characterization).

**"Too dense" defined concretely**: a concept with 50 edges but 45 of them in the SAME bucket (e.g. 45 near-duplicate Synonym/RelatedTo edges, exactly the CSKG lexical-dilution pattern the 2026-07-10 gate note already diagnosed and stripped) is measured as LOW type-diversity despite high raw degree — this is the same failure mode from the other direction, and the metric must catch both: raw-degree-high-but-type-diversity-low (redundant/over-dense) and raw-degree-low (sparse/under-characterized) are BOTH failures under this target, only raw node-count/aggregate-k-core is not.

**How the earlier k-core/aggregate-density finding relates, not contradicts**: the CSKG k=12-14 dense band (10,731-23,632 nodes @ avg-deg 38-55) is a NECESSARY-BUT-INSUFFICIENT correlate — high-degree nodes are more LIKELY to span multiple relation-type buckets (more edges gives more chances to hit different buckets), but a node could in principle have high raw degree entirely within one bucket (pure synonym hub) and still fail the real per-concept-characterization target. **The aggregate k-core measurement stays useful as a cheap first-pass filter (Section 6's cheap decisive test still starts there) but must be followed by a per-concept type-diversity measurement, not treated as sufficient on its own.** This is the honest correction to the first-pass draft's framing.

**Concrete measurable procedure**: for each core entity, compute the SET of distinct relation-type buckets it has >=1 edge in (out of the applicable buckets for its category), report the fraction of core entities clearing the >=4-5-of-applicable-buckets bar, and separately report the fraction whose edges concentrate (e.g. >80%) in a single bucket despite otherwise-adequate raw degree (the redundancy flag). This is the actual "coverage/density audit" the cheap decisive test below performs.

## 2. Multilingual plan — concept-centric, per BabelNet/Wikidata precedent

**Model**: one language-independent concept identity (a QID-or-synset-style node) carries a set of multilingual LABELS as an attribute (label + language tag + optional gloss-per-language), exactly Wikidata's existing `labels`/`aliases`-per-language-code design and BabelNet's synset-with-multilingual-lexicalizations design — **this is not a new mechanism to invent, it is adopting an already-proven, already-precedented data model wholesale.** A concept is NOT duplicated per language; only its label surface changes.

**Culture-specific concepts as genuine exceptions**: where no cross-lingual synonym exists for a concept (BabelNet's own merge algorithm handles this by NOT force-mapping a Wikipedia sense to a WordNet synset when no genuine correspondence exists), the concept gets its OWN dedicated core node rather than being awkwardly folded into a near-but-not-quite equivalent from another language/culture. Concrete examples worth seeding: Danish "hygge," Portuguese "saudade," Japanese "ikigai," philosophical/social concepts like "ubuntu" (Southern African) — these are genuinely non-reducible and should be first-class core nodes, not module attachments (they are general commonsense/cultural concepts, not domain-technical ones).

**Beyond-brain coverage, concretely**: superhuman coverage on the multilingual axis means drawing concepts (not just translations of English concepts) from BabelNet's ~600-language span and Wiktionary's dense multilingual sense inventories — surfacing genuinely distinct concepts that a monolingual human's commonsense vocabulary would never encounter, not merely relabeling the same English-centric concept set in more languages. **Where this adds reasoning value vs. sparse tail**: exactly the Section 1 criterion — a culture-specific concept earns its place if it clears the per-concept characterization bar (has taxonomic placement + property/causal/social edges of its own), not merely by existing as a labeled entry with no characterizing relations (which would reproduce the degree-1 tail problem in a new guise).

## 3. Module registry spec — open admission, no core rewrite

**Direct structural mirror of the brain-side finding** (`research_brain_grounding_flexibility_open_spoke_registry_2026-07-14.md`): that note found the brain's grounding architecture stays extensible not via a fixed channel taxonomy but via a generic ADMISSION TEST any new candidate spoke must pass (contingency: reliably co-varies with existing grounded content; active-loop: exercised via query-and-check, not passively pasted in). This spec adopts the identical shape for KG modules:

**A module is a runtime-registered tuple**: `(module_id, entity_anchor_map, relation_vocabulary, provenance/measurement-type)`. A candidate module is admitted if it passes:

1. **Anchoring test** — a nontrivial fraction of its entities can be reliably resolved (via existing identity links, or embedding-similarity + validation per Section 5's methodology) to EXISTING core entities. A module whose entities mostly fail to anchor to the core (e.g., a purely novel, unlinked entity set) is not admitted as a module — it would need its own core-extension work first, a structurally different and more expensive operation.
2. **Non-redundant-content test** — the module supplies attribute/relation types NOT already covered by the core or by an existing module (per Section 0's explicit core-vs-module resource split) — prevents duplicate/competing modules for the same content (e.g. two separate "melting point" sources without a declared precedence).
3. **Declared provenance/measurement-type** — every module states whether its content is MEASURED (instrument-derived, e.g. PubChem experimental properties), RATED (human-normed, e.g. Lancaster sensorimotor norms), or DERIVED/CURATED (e.g. GeoNames feature-type taxonomy) — this classification is what Section 5's cross-module reconciliation uses to arbitrate collisions.

**What admission does NOT require**: touching the core's schema, relation vocabulary, or existing entity set. This is the concrete "no core rebuild" property — a module is pure ADDITION (new entities/attributes anchored onto existing core nodes, or occasionally a small number of genuinely new domain-specific entities that themselves get anchored via a taxonomic parent already in core, e.g. a specific chemical compound anchored under core's existing "chemical substance" class).

**Removal/non-interference test (directly reusing the brain-side note's cheap decisive test shape, adapted to KG modules)**: registering a new module must NOT measurably degrade core relational-inference performance on held-out core-only queries (analogous to the brain-side "spoke A's performance is unchanged after spoke B is registered"). This is a genuine, cheap, falsifiable test to run once any second module is added — HARD-FAIL here would mean the "open registry, no core rewrite" claim doesn't hold in practice and modules are secretly coupling to core internals.

## 4. Cross-module interconnection — through shared core entities, not module-to-module links

**The "diamond" example, made concrete**: the core entity "diamond" (taxonomically: instance-of mineral/gemstone, already core-characterized with property/use edges from ConceptNet-class content) gets THREE separate module attachments anchored to the SAME core node: (a) a materials-module attachment carrying hardness (Mohs 10), crystal structure, thermal conductivity; (b) a chemistry-module attachment (PubChem) carrying molecular composition (pure carbon, sp3 lattice); (c) potentially a commerce/geology-module attachment (not yet specified) carrying formation conditions or market-use facts. **No module ever links directly to another module** — chemistry-module and materials-module content never reference each other; they are both anchored to "diamond" independently, and any apparent chemistry-materials relationship is mediated ENTIRELY through the shared core node, not through a direct edge between the two modules' data.

**Why this is the right design, not just a convenience**: it means adding a NEW module (say, a jewelry/commerce module) never requires updating the materials or chemistry modules' code or data — it only requires anchoring the new module's entities to core, exactly the admission test in Section 3. This is the concrete mechanism that makes "add a domain without rebuilding the core" true rather than aspirational.

**Overlap/collision reconciliation (the concrete cost of modularity, addressed directly)**: the genuine hard problem is when TWO modules both assert an attribute of the SAME TYPE for the SAME core entity (e.g. a materials module and a chemistry module both provide a "density" value for "diamond," possibly from different measurement conditions or slightly different numeric precision). Reconciliation procedure, directly reusing the merge-methodology precedent from Section 5 below:

1. **Detect the collision** — same core-entity + same-attribute-type asserted by >1 module (a cheap, purely structural check, no domain reasoning required).
2. **Classify by declared provenance type** (Section 3's module metadata) — MEASURED-vs-MEASURED collisions (two experimentally-derived values) are adjudicated by numeric-tolerance check (values within expected measurement variance -> keep both, tag as corroborating; values genuinely conflicting -> flag for curation, do NOT silently average). MEASURED-vs-RATED or MEASURED-vs-DERIVED collisions default to preferring the MEASURED value (directly analogous to Dong et al.'s accuracy-weighted-source-trust principle, Section 5) but retain the other as a secondary/lower-confidence attachment rather than discarding it.
3. **Apply YAGO4-style hard constraints where domain logic permits** (e.g. a materials-module "melting point" and a chemistry-module "boiling point" for the same substance must satisfy melting < boiling — a cheap disjointness-style sanity constraint) — flag violations as detected contradictions requiring resolution, exactly YAGO4's constraint-enforcement mechanism (Section 5), applied at cross-module-collision granularity specifically rather than at whole-source-ingest granularity.
4. **Report the reconciliation outcome explicitly** (not silently) — per Section 5's "fully vetted is a set of measured tradeoffs, not an absolute" finding, every cross-module collision resolution should be logged with which value was kept/demoted and why, giving the same kind of honest cost-accounting YAGO4/CSKG/BabelNet already model at the whole-source level.

## 6. Merge + vet methodology (entity anchoring + collision reconciliation, the mechanism behind Sections 3-4)

**Entity resolution/anchoring** — two-tier approach, precedented by CSKG's own practice: (a) where a pre-existing clean cross-reference table exists (WordNet ILI, Wikidata external-ID/sameAs statements), use it directly — zero-noise, zero-cost, this is how a module's entities should FIRST be attempted to anchor to core; (b) where none exists (CSKG's own WordNet-Wikidata case), embedding-similarity linking + mandatory human/automated validation, accepting a real, quantified precision cost (CSKG's own reported ~51% raw precision, corrected to a smaller validated set by discarding the rest). **BabelNet's WSD-based merging claims higher precision (>99.5% on a validated subset) but over a narrower resource pair — treat as an upper-bound existence proof, not a default expectation** for arbitrary module-to-core anchoring.

**Relation-vocabulary normalization** — no automated standard method found; every precedent (CSKG's 58-relation ConceptNet-centric vocabulary, YAGO4's manual schema.org-to-Wikidata mapping) is MANUAL curation with admitted granularity/information loss (CSKG folds WebChild's 19 property relations into one generic HasProperty; Wikidata's ~101k CS-relevant statements collapse to 15 ConceptNet relations). Modules should declare their OWN relation vocabulary (Section 3) rather than being forced into the core's 58-relation set — this avoids the granularity-loss problem for domain-specific relations (a chemistry module's "boiling_point" relation stays distinct, rather than being collapsed into core's generic HasProperty) while still anchoring the ENTITY to core.

**Conflict/contradiction detection and resolution** — two established mechanisms, both directly reused in Section 4's cross-module reconciliation: (a) **hard logical constraints** (YAGO4's OWL2 DisjointClasses/domain-range/cardinality + SHACL shapes) — precise but expensive, YAGO4 dropped 28% of all Wikidata facts enforcing this; (b) **probabilistic/statistical fusion** (Google's Knowledge Vault/Knowledge-Based Trust line, Dong et al. 2014/2015) — accuracy-weighted source-trust scoring beats naive majority voting.

**"Fully vetted" definition** — the field's own quality-assessment literature (23-dimension taxonomy, reduced in practice to accuracy/completeness/consistency/timeliness/provenance) makes clear no source (CSKG, BabelNet, YAGO4) satisfies all dimensions simultaneously — each explicitly trades one for another (YAGO4's 28% fact-loss for consistency; CSKG's 51% raw entity-link precision; BabelNet's sub-0.5 recall, language-imbalanced 93.9% Spanish vs 17.5% Urdu coverage). **"Fully vetted" should be operationalized as an explicit, reported tradeoff — our own core-merge and every module-admission event should report the SAME kind of honest cost numbers, not claim unqualified completeness.**

## 7. Cheap decisive test (pre-registered — this is the FIRST buildable step)

**Recommended FIRST STEP, updated per the per-concept-characterization correction (Section 1)**: a two-part audit of our OWN currently-ingested active partition (~190k edges, 141,511 nodes, 59% degree-1), zero new data acquisition.

**Part A (coarse, cheap, reuses existing method)**: recreate the same Batagelj-Zaversnik k-core decomposition already specified and run once against the full external CSKG download in the 2026-07-10 gate note (the script itself, `scratchpad/kcore.py`, was written in a prior session's scratchpad and is not confirmed to persist on disk this session — treat as "recreate the ~50-line numpy-CSR method already fully specified in that note," not "reuse a surviving file"). Run it against our own active partition. Report the k-core table (nodes @ avg-deg per k) and compute overlap with CSKG's already-identified k=12-14 dense band (10,731-23,632 nodes @ avg-deg 38.4-55): how many of those already-known dense-band nodes are present in our partition, and at what k-core level do they sit in OUR graph specifically.

**Part B (the corrected, load-bearing measurement, per Section 1)**: for a sample of core entities in our active partition, compute the per-concept relation-TYPE-bucket coverage (Section 1's table) — what fraction of entities clear the >=4-5-of-applicable-buckets bar, and separately, what fraction of entities have high raw degree but low type-diversity (the redundancy-flag population). **This is the measurement that actually answers "how sparse is our sparse tail, and is our non-sparse population genuinely well-characterized or just high-degree-in-one-bucket."** Part A alone (as in the original draft) would under-diagnose a graph that has adequate aggregate density but poor type-diversity; Part B is the corrected, load-bearing test.

## Falsifiable predictions (HARD-PASS / HARD-FAIL)

**HARD-PASS (the two-part audit confirms an actionable ingest-gap story):**
1. A meaningful fraction (>=30%) of CSKG's already-known k=12-14 dense-band nodes are ABSENT from our active partition, or stranded at low k-core because dense-band neighbors weren't co-ingested (Part A).
2. The per-concept bucket-coverage measurement (Part B) shows our 59%-degree-1 population clusters overwhelmingly at 1-of-N applicable buckets (almost always just taxonomic), confirming the pathology is exactly "under-characterized," not merely "low count" — a distinction that matters because the fix (add missing relation TYPES, not just any edges) is different in each case.
3. A meaningful fraction of our HIGH-degree nodes show the redundancy-flag pattern (>80% of edges in one bucket) — if found, this identifies a SECOND distinct fix needed (de-duplicate/de-emphasize redundant same-bucket edges), not just an ingest-more story.

**HARD-FAIL (informative negatives — do not force either story if these occur):**
1. Our active partition's dense-band overlap with CSKG's k=12-14 nodes is near-total (>=80%) AND our bucket-coverage measurement already shows most non-degree-1 entities clearing the >=4-5-bucket bar — would mean the core is already reasonably well-built and the 59%-degree-1 tail is a genuinely separate, second-order problem (true long-tail coverage gap, not a missing-dense-band problem), redirecting effort toward targeted module/entity additions for specific under-covered categories rather than a bulk core re-ingest.
2. The redundancy-flag population (Part B, prediction 3) is near-zero — would mean the CSKG-style lexical-dilution pattern does NOT recur in our own ingest, a genuinely different (and reassuring) finding worth confirming rather than assuming by analogy.
