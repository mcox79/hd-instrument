# Research: reader load-reduction WIN-PATH -- collapsing dim_needed from ~79k to a feasible dimension

**Filed by:** research sub-agent. **Trigger:** `exp_grounding_multihop_decisive_win_v1` FULL landed `MIDDLE_BAND_PARTIAL_CROSSING` (`data/exp_grounding_multihop_decisive_win_v1/metrics.json`): best arm `N_SCALE` (8x dim, 2048) reached reach2=0.172 (still short of the WIN bar reach2>=0.60), `regime=INCIDENTAL_CROSSTALK` (aliasing_frac=0.283), and the diagnostic readout `load_base=17.34 load_scale=2.168 above_thr=True dim_needed=79286 (thr=0.056)` names the wall explicitly: a capacity/load ceiling, escapable in principle, but 8x dim was ~40x short of the naive full-codebook bound. This drill asks: what is the biggest lever to cut `dim_needed` itself, not just throw more dimension at the existing (pessimistic) formula.

**Method:** 3 parallel Sonnet lit-scan sub-agents, one per angle (sparsification; decorrelation/decoupling; structured/high-capacity codes). Generic math/CS query terms only, no substrate-specific mechanism names or numbers off-platform, per query-privacy discipline.

## HEADLINE

**The naive 79,286-dim bound is dominated by CODEBOOK COUNT, not codebook correlation -- and the count term is inflated by roughly 670x because it charges the resonator against the FULL global vocabulary (n_nodes=4440) when the true per-hop competing set is the LOCAL GRAPH NEIGHBORHOOD (mean_degree=6.65).** Reworking the same formula the metrics.json already computes -- `dim_needed = D_f / 0.056` (Frady/Kent/Olshausen/Sommer 2019 resonator-stability threshold, independently re-verified this cycle via direct fetch of arXiv:1906.11684: the exact ratio is `D_f/N <= 0.056`) -- with `D_f` set to the *local* branching factor instead of the *global* node count collapses the bound from ~79k to double digits/low hundreds, comfortably inside any feasible dimension. Sparsification (angle 1) and structured/exponential-capacity codes (angle 3) are real, but they are second-order multipliers on the *correlation* tax, not fixes for the *count* tax that is actually dominating our number -- and lit-scan 2 independently confirms these are mechanistically distinct fixes for distinct terms, not substitutes for each other.

**This flips the "8x dim wasn't enough" reading:** the Stage-5 cell didn't fail because dimension-throwing is the wrong lever in general -- it failed because it scaled dimension against a formula that was still charging crosstalk against the wrong (global) competing set. The dominant lever is architectural (restrict the candidate set the cleanup/resonator discriminates against to the graph-local neighborhood at each hop), not a bigger dimension.

## The capacity math (redo of the metrics.json formula with the corrected D_f)

The existing diagnostic (`data/exp_grounding_multihop_decisive_win_v1/metrics.json`, `df_over_n` block) computes `load(dim) = D_f / dim` with threshold 0.056, giving `dim_needed = D_f / 0.056`. Back-solving the two reported points confirms `D_f = 4440` exactly (`load_base=17.34` at dim=256 -> `17.34*256=4439.04`; `load_scale=2.168` at dim=2048 -> `2.168*2048=4440.06`) -- i.e. **the naive bound is charging crosstalk against the full node vocabulary (n_nodes=4440 in `subgraph_meta`)**, treating every retrieval as if it must stay discriminable from all 4440 stored concepts simultaneously.

Substituting the graph-local competing set (already reported in the same `subgraph_meta` block) instead of the global count:

| D_f source | D_f value | dim_needed = D_f/0.056 | vs. current dims tested |
|---|---|---|---|
| Global vocabulary (naive, current) | 4440 | 79,286 | ~40x short even at 2048 |
| 1-hop local neighborhood (mean_degree) | 6.65 | 119 | already satisfied at dim=256 |
| 2-hop local neighborhood (~mean_degree^2, upper bound) | ~44 | 789 | satisfied well under 2048 |
| 3-hop local neighborhood (~mean_degree^3, upper bound, real graphs will be lower due to overlap/clustering) | ~294 | 5,250 | satisfied at <=8k |

Even the deliberately pessimistic 3-hop upper bound (treating the local tree as if it never re-converges, which real ConceptNet subgraphs will not do -- `frac_deg_ge_2=1.0` means every node has repeat structure, so real branching is lower) lands at 5,250 -- inside the <=8k target with margin, and the 1-2 hop case (the actual reach2/reach3 WIN bar) is inside <=1k. **This is not a marginal improvement: the count-term correction is a ~670x reduction in D_f, translating linearly into a ~670x reduction in dim_needed, which dwarfs anything sparsification (a log-factor/constant-factor win per lit-scan 1) or structured-code capacity (which degrades under correlation anyway, per lit-scan 3) can deliver on their own.**

## ONE concrete code-design for the next win-cell

**Local chain-index + global semantic layer (two-layer decoupled design), buildable directly on the existing `exp_grounding_multihop_decisive_win_v1` harness:**

- **Layer A (chain-index, near-orthogonal, low-load):** at each hop, restrict the resonator/cleanup step's competing candidate set to the current node's actual graph neighbors (and optionally their neighbors for 2-hop lookahead), not the full stored vocabulary. This is a legitimate, not oracle-cheating, restriction for multi-hop KG traversal specifically -- the whole point of walking a graph is that adjacency is known at each step; this is the direct VSA/resonator analog of what HippoRAG (arXiv:2405.14831, lit-scan 2, index-only verified) already does for LLM-embedding-based multi-hop RAG: a discrete graph-structured index layer (their Personalized-PageRank-over-KG) sits in front of the dense semantic-embedding layer, so retrieval never scores against the full embedding vocabulary. Bind/unbind this local layer with block-sparse local-circular-convolution (LCC) binding (Frady/Kleyko/Sommer, arXiv:2009.06734, fetched and re-verified this cycle) since it is the one binding scheme lit-scan 1 confirmed *preserves sparsity exactly* under composition (generic sparse binding densifies -- term count grows ~R^2 per bind -- and loses its capacity edge; block-structured sparsity does not).
- **Layer B (semantic, correlated, existing):** keep the current correlated ConceptNet embedding codes exactly as-is for the actual relation/meaning content -- this is what retrieval/generalization needs and what the CORRELATION-HURTS-CAPACITY finding says must stay correlated.
- **Link:** a discrete lookup/pointer keyed by node identity (not a continuous/generalizing map) from the Layer-A local-index code to the Layer-B semantic code. Keeping this interface discrete (a table, not an associative bind) is the specific design choice that avoids re-introducing correlation-crosstalk at the seam (see Honest risk below).

**One-line discriminator:** `reach2`/`reach3` fidelity when the cleanup/resonator candidate set is restricted to true graph-local neighbors (Layer A) at the SAME or LOWER dimension than the already-tested 8x arm (2048, or even the 1x baseline 256) should clear the WIN bar (reach2>=0.60) because the corrected `dim_needed` (119-789 for 1-2 hop) is already satisfied at existing dimensions -- HARD-PASS if reach2>=0.60 at dim<=2048 with the local-restriction change alone (no dimension scaling needed); HARD-FAIL if reach2 stays in the 0.10-0.20 range seen in the already-landed arms even after restricting to true local candidates, which would mean the wall is NOT primarily the global-count term and the `D_f=n_nodes` back-solve was a coincidence rather than the true mechanism (see Honest risk).

**Prediction 1 (count-term dominance):** Recomputing `df_over_n` with `D_f` = actual per-hop local candidate-set size (not `n_nodes`) on the already-landed metrics shows `dim_needed` collapses to <=1000 for reach2 and <=8000 for reach3.
- HARD-PASS: recomputed `dim_needed` (reach2, 1-hop local D_f) <=1000 AND the harness confirms its current cleanup step in fact scores against the full n_nodes vocabulary (i.e., the fix is real, not already-applied-and-ineffective).
- HARD-FAIL: the harness already restricts scoring to local candidates (D_f was never n_nodes in practice) and `dim_needed` was already computed correctly -- would mean the wall is NOT a count-term artifact and the naive-bound story in this note is wrong; must fall back to angle 1/3 (sparsification + structured-code) as the only remaining levers, at much smaller expected gains (log/constant-factor, per lit-scan 1 and 3).

**Prediction 2 (local-restriction cell clears the WIN bar without new dimension scaling):** A `LOCAL_INDEX` arm -- identical harness, cleanup/resonator restricted to true graph-neighbor candidates, held at the CURRENT baseline dimension (256) or the already-tested 2048 -- clears reach2>=0.60, reach3>=0.35, gain2>=0.30, slope-flatten>=40% (same WIN bands as the landed cell).
- HARD-PASS: LOCAL_INDEX arm clears all four WIN bands at dim<=2048 (i.e., wins WITHOUT the 8x-or-more dimension scaling the naive bound demanded).
- HARD-FAIL: LOCAL_INDEX arm fails to clear reach2>=0.15 (the existing FAIL_REACH2 band already in the cell's bands config) even with true local-candidate restriction -- would mean residual crosstalk within the LOCAL neighborhood itself (real semantic overlap among genuinely-related, graph-adjacent concepts, e.g. multiple true relations connecting the same node pair) is the actual floor, not global-vocabulary count. This is the CORRELATION tax reappearing at small scale, and would validate the honest risk below rather than refute the count-term diagnosis.

**Prediction 3 (block-sparse LCC binding for Layer A preserves the gain under chaining):** Using block-structured sparse binding (not dense HRR-style binding) for the local-index layer preserves reach2/reach3 fidelity across 2-3 sequential hops (not just a single simultaneous multi-factor bind) at equal or better fidelity than dense binding at matched dimension.
- HARD-PASS: block-sparse LCC-bound LOCAL_INDEX arm's reach3 >= dense-bound LOCAL_INDEX arm's reach3 at matched dim.
- HARD-FAIL: block-sparse binding degrades faster than dense binding across sequential (not simultaneous) hops -- would confirm lit-scan 1's flagged gap (published sparse-block capacity results are for simultaneous multi-factor binds, not iterative sequential re-binding) applies here, and dense binding should be kept for Layer A despite its slightly lower per-dimension capacity.

P_deflated (LOCAL_INDEX two-layer design clears the real WIN bar, reach2>=0.60, at feasible dim<=8k): **0.38** (base intuition ~0.55-0.65 -- the capacity math is a clean, mechanically-verified re-derivation of the EXISTING landed diagnostic formula, not speculative, and the two-layer pattern has a genuine validated precedent (HippoRAG) in a closely analogous setting; deflated 0.20 per lit-scan calibration penalty because no source in any of the 3 scans tests this exact design -- graph-structured index + VSA/resonator binding -- combined; HippoRAG's precedent uses dense LLM embeddings + PageRank, not resonator/VSA cleanup, so the transfer is an analogy, not a proven equivalence). ## Honest risk (the crux, resolved without hedging the ambition)

**Does restricting the candidate set trade away the semantic correlation retrieval needs? Answer: only if the interface between the two layers is designed as an associative/generalizing map -- and it doesn't need to be.** The crux tension stated in the task -- retrieval needs semantic correlation, chaining is hurt by it -- resolves cleanly once COUNT and CORRELATION are treated as the two distinct terms lit-scan 2 confirmed they are (a genuine literature-backed distinction: decorrelation fixes the correlation-tax; it does NOT fix the count-tax, and vice versa). The design above never asks the chain-index layer to decorrelate anything -- it keeps the correlated semantic codes fully intact in Layer B, untouched, exactly as capacity-costly and exactly as retrieval-useful as they already are. Layer A only shrinks the SET SIZE the resonator must discriminate against at each hop, using information (graph adjacency) that a multi-hop KG traversal legitimately has. **The correlation problem does not have to be solved for this fix to work -- it is sidestepped, not decorrelated away**, which is the honest reading of why this differs from (and is cheaper than) every previous cleanup-architecture attempt (per-hop DG-gate, CA1-comparator, dense-Hopfield cleanup) that tried to fight the correlation directly.

Where the risk genuinely reappears, per lit-scan 2's explicit, unresolved flag: **the interface mapping from index-code to semantic-code.** If that mapping is built as a second associative/generalizing structure (e.g., trying to make it "fuzzy" so novel/unseen nodes route correctly), the correlation-crosstalk problem re-enters exactly there, because now the interface itself has to discriminate among correlated things. The mitigation is architectural discipline, not a proof: keep the interface a **discrete lookup keyed by node identity** (a table, not a bind/unbind or similarity-based map) -- discrete lookups have no correlation-crosstalk failure mode because there is no continuous similarity computation at that step. This is buildable directly (every node in the existing ConceptNet subgraph already has a stable identity/index), but it does mean the design as stated does NOT generalize to genuinely novel, never-indexed entities without a separate mechanism -- that is an honest, named limitation, not a hidden one, and it does not affect the reach2/reach3 WIN-bar test (which operates over the already-indexed subgraph).

A second, smaller residual risk (flagged by Prediction 2's HARD-FAIL branch): even after restricting to the true local neighborhood, SOME of that local crosstalk is genuinely semantic (two true relations connecting the same adjacent node pair, e.g. a concept that is both `CN_USED_FOR` and `CN_CAPABLE_OF` the same neighbor) -- this residual is the correlation-tax lit-scan 2 identified, now operating at a MUCH smaller scale (tens, not thousands, of competing items), where sparsification (angle 1, block-LCC) and structured/exponential-capacity cleanup (angle 3, dense-Hopfield, already partially tested in the landed cell's `DENSE_HOPFIELD` arm) become the right complementary tools -- because at local scale their log/constant-factor gains are no longer swamped by a 670x count-term gap.

## Intuitive summary

**What we did:** the last experiment told us our multi-hop reasoning is stuck below a hard capacity ceiling -- and gave us an exact, uncomfortable number for how big we'd need to make things to escape it (about 79,000 dimensions, roughly 40x bigger than what we'd already tried). Rather than accept that number and start planning how to afford it, we asked: is that number even measuring the right thing? We sent three parallel searches out -- one on whether making signals sparser helps, one on whether separating "how we index/chain memories" from "what memories mean" helps, and one on whether fundamentally different, higher-capacity memory designs help.

**What we found:** the 79,000 number turns out to be measuring something needlessly pessimistic. It assumes that every single retrieval step has to stay distinguishable from every one of the roughly 4,440 concepts we've ever stored -- as if you had to keep a fact clearly separate from every other fact you know, every time you recalled anything. But in a real multi-hop chain, you're walking a graph: at each step you only need to distinguish among the handful of neighbors actually connected to where you are (on average about 7), not all 4,440. Doing the same arithmetic the failed experiment already used, but with that correction, the required size drops from 79,000 down to around 100-800 -- smaller than what we've already been using. That's not a small tweak; it's roughly a 670-times overcorrection in the original estimate.

**Why it matters:** this means the fix isn't "spend a lot more compute" (yesterday's plan) -- it's "build a small local lookup/index layer that only ever compares a memory against its true neighbors, and keep the rich, meaning-carrying (but capacity-costly) representations completely separate and untouched." This exact two-layer pattern -- a cheap, discrete index layer plus a separate rich semantic layer -- is already how the hippocampus is believed to work, and it's already how modern large-scale search engines are built (a fast index narrows candidates before a slower, richer comparison runs). We found real, published precedent for it. The honest catch: this only works cleanly if the "lookup" between the two layers stays a simple, exact address book rather than trying to be clever/fuzzy about it -- if we ever need it to generalize to brand-new, never-seen concepts on the fly, the hard problem could sneak back in at that handoff point. And even after this fix, a small amount of genuine, real overlap between closely related facts will probably remain (two things can genuinely both be true about the same neighbor) -- but at that much smaller scale, the sparsity and richer-cleanup tricks we already had waiting in reserve are exactly the right size of tool to mop it up.
