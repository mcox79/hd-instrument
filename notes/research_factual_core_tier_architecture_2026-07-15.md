## HEADLINE

**The factual core should be built as its OWN `AdditiveKGMap` instance (same class already live for the reasoning mechanism, zero new code), entity-keyed by canonical hub IDs, fit in periodic BATCH-CONSOLIDATION cycles (CLS-aligned: interleaved, not sequential-online) — and its product value should be judged on canonical-ID coverage/density and interference-free auditability, NOT on beating a frequency baseline at single-relation inference (that fight is mathematically capped and already lost per the v3 single-relation refute).** The core's real reasoning contribution is upstream of prediction: it supplies the canonical-ID population, the per-entity "constituent feature" vector, and a warm-start coordinate that conjunction modules compose over — i.e. the core is infrastructure FOR the conjunction modules' genuineness, not a competing predictor. The cross-module hub-identity design already specified for modules (2026-07-15 drill) applies unchanged to the core: it is just another spoke that happens to be broad and LLM-generated rather than narrow and measured.

## 1. Value proposition + honest scope

Three targets, ranked — do not chase the first thing that looks like "accuracy":

1. **PRIMARY — canonical-ID coverage and per-entity density.** This is the metric the reachability-audit tool (already specified, not yet built, per the grounding-subsumed drill) and a new density-audit extension (section 3 below) will actually measure. The core's job is to get as many hub entities as possible above the biological density floor (~13.4 attributes, >=3 relation-categories, >=6 independent exposures per concept — `drill_brain_grounded_data_composition...`), because reachability/density is what the same-day grounding-subsumed drill shows is the actual discriminator for relational-inference quality (GROUNDED_ONLY 0.618 vs RELATIONAL 0.387 pattern), not raw fact count and not single-relation predictive accuracy.
2. **SECONDARY — interference-free, glass-box storage/retrieval.** The differentiator against an LLM's parametric memory is that a fact here is inspectable, editable, deletable, and provenance-stamped — this is the CHAIN_GRADE pattern-separation hedge already banked, and it holds regardless of whether the core beats frequency on any given relation. Frame this as the product story, not "smarter facts."
3. **TERTIARY but the one that closes the loop with reasoning — compositional substrate for conjunction modules.** Every conjunction-module row (per the registry note, section 2) needs "constituent features (the factors whose combination determines the target)." Right now each module invents its own ad hoc feature set from within its own dataset. The factual core's per-entity coordinate/fact-set is a natural, STANDARDIZED source of constituent features for ANY entity that also carries a canonical ID (a gene's core facts — is-a-kinase, part-of-pathway-X, chromosome-location — are exactly the kind of "constituent feature" a conjunction module's strong-additive baseline should be allowed to condition on). This turns "the core happens to share entities with modules" into "the core is a feature-supply service the module registry schema already has a slot for." Flag as a testable proposal (see linchpin), not yet proven.

**What NOT to optimize for:** single-relation held-out link prediction accuracy against a frequency/popularity baseline. That fight is already closed (memory: single-relation homophily-solvable, v3 REFUTED; "prize = CONJUNCTIONS"). Don't let a future cell frame the factual core's success metric as "beats FREQ on relation R" — it will lose that fight structurally regardless of build quality, and losing it says nothing about whether the core is doing its actual job (density, auditability, feature supply).

## 2. Seamless integration with the reasoning mechanism — concrete, code-level

Read `hdlab/additive_map.py` directly (the live `AdditiveKGMap` class, VET-confirmed CHAIN_GRADE, MRR 0.128 real-data) rather than reasoning abstractly about "role-filler bindings." Its actual API:
- Entities are looked up by **string label** via `entity_to_idx: Dict[str, int]` (`fit()`, `_eidx()`). Relations likewise via `relation_to_idx`.
- Composition is literal coordinate arithmetic: `score(t) = -||X_h + D_r - X_t||`; a novel entity's code is `compose_entity()` = mean over support edges of `X_h + D_r` (zero-training, degree-invariant); `insert_entity()` appends a row to X with no fixed-codebook limit.
- Persistence (`save`/`load`) round-trips `X`, `D`, and both index maps.

**This is the entire cross-module interface, already built, if and only if every module's `entity_to_idx` string keys are the SAME canonical-ID strings** (the hub-identity design from the cross-module drill, section 4/5). Concretely:
- **Instantiate one `AdditiveKGMap` per tier/module** (factual-core map; module-#1 Costanzo map; module-#2 BioGRID map; ...), each with its own `X`, `D`, own relation vocabulary, own `k`. This matches Rank-1 from the cross-module drill (hub-identity + spoke-relation, NOT one merged graph) exactly — no new abstraction needed, just discipline in what string you pass as `entity`.
- **Cross-tier/cross-module query = identity-anchored traversal across separate maps**, exactly as the cross-module drill's bind/unbind description, made literal: `score_all()`/`compose_entity()` in map A to find a partner entity label -> check `partner_label in map_B.entity_to_idx` (pure dict membership, the "cheap deterministic identity join" the drill calls for) -> if present, continue natively in map B (`map_B.score_all(partner_label, relation)`). No merged embedding space, no learned alignment step, matching Rank-1/ARAX-style traversal.
- **Warm-start is a free byproduct of `compose_entity()`.** When module #1 (or #2) first encounters a gene that already has core facts, its initial conjunction-module-local coordinate can be seeded via `compose_entity()` called with core-map support edges reaching that entity (is-a, part-of, encodes), THEN the module's own measured-interaction edges are fit/composed on top. This is the "constituent-feature backbone" from section 1.3 made concrete: the seed literally comes from the core map's `X_h + D_r` estimates, not a hand-built feature vector.
- **Condition, not assumption:** this only works because `entity_to_idx` is a bare string->int dict with no schema validation. The discipline that makes it work is entirely upstream — every ingest/generation pipeline (core AND modules) MUST resolve to canonical IDs (HGNC/SGD-ORF/InChIKey/etc, per the crosswalk sources already named in the cross-module drill) BEFORE calling `.fit()`, never local/display names. This is a generation-prompt and ingest-pipeline discipline, not a code change.

## 3. Crispness + provenance + coverage

**Crispness gate — a relation-type ALLOWLIST, not a post-hoc filter.** The epistasis LLM-gen trap (memory: 2 generation clusters, both additive-capturable) traces to debatable/narrated severity relations. For the factual core, restrict LLM generation to relation CATEGORIES that are non-debatable by construction:
- taxonomic (is-a, subclass-of, instance-of)
- compositional (part-of, has-component, encodes, contains, located-in)
- definitional (defined-as, synonym-of, abbreviation-of)
- quantitative-measured (has-numeric-property + unit — generate ONLY when cross-checkable against a canonical snippet, e.g. molecular weight, chromosome coordinate)
- Reserve CAUSAL relations (causes, treats, associated-with-disease) as a SEPARATE, flagged-for-cross-check category — these are exactly the ones that produced debatable severity in the epistasis case; do not free-generate them at the same trust tier as the four categories above.

**Provenance (per fact/row), mirroring the module registry's per-row discipline (registry note section 2) applied to generation instead of dataset ingest:** generation model + prompt-template version + generation date + relation-category tag (from the allowlist above) + a binary cross-check flag (was this spot-checked against an external canonical source, e.g. a Wikidata/UniProt/ChEBI snippet, yes/no). Re-vettable exactly like the module registry: if the generation prompt or model changes, the batch is versioned, not silently overwritten.

**Density measurement — extend the reachability-audit tool rather than building a second tool.** The grounding-subsumed drill already specifies (and has NOT yet built) a k-hop reachability-audit walking from every hub entity to the nearest measured node. Extend that SAME traversal to also emit, per entity, across ALL registered maps (core + every module):
- **attributes** = count of distinct (relation, value) facts touching this canonical ID
- **modalities (proxy)** = count of distinct relation-CATEGORIES touched (from the 5-category taxonomy above, plus "measured-interaction" for conjunction-module facts)
- **exposures (proxy)** = count of distinct generation-batches / dataset-rows / source-provenance-IDs touching this entity (independent corroborating mentions, not just fact count)

Target floor (from `drill_brain_grounded_data_composition_type_scope_growth_2026-07-15.md`): **>=13 attributes, >=3 categories, >=6 exposures** marks an entity as "densely grounded," distinct from merely "reachable" (grounding-subsumed drill's weaker k<=2-hop bar). Track the density-floor-attainment curve as core generation proceeds — this is the concrete, measurable target the PIVOT's "how much is enough" question was missing.

## 4. Brain-ground

**Two brain mechanisms apply at different levels, and conflating them is the mistake to avoid (same pattern as the cross-module drill's TEM-vs-ATL distinction):**

- **ATL hub-and-spoke** (already established, `drill_cross_module_interface...`) answers WHERE identity lives (one shared transmodal hub, domain content bound on via CDZs) — this is the cross-module/cross-tier interface answer from section 2 and needs no new grounding here.
- **Complementary Learning Systems (CLS)** answers HOW the core should be BUILT AND UPDATED over time, which the prior drills did not address (they cover the interface, not the update dynamics). CLS's core claim (McClelland, McNaughton & O'Reilly 1995, *Psychological Review*): a network that learns new items fast and non-interleaved destroys previously-learned distributed structure (catastrophic interference, McCloskey & Cohen 1989) — the neocortex is a SLOW learner that extracts shared structure only via many INTERLEAVED exposures, while the hippocampus is a separate fast, sparse, one-shot binder; hippocampal replay (especially during sleep) provides the interleaving that lets cortex assimilate new content without overwriting old structure. Kumaran, Hassabis & McClelland (2016, *Trends in Cognitive Sciences*) extends this directly to artificial systems, explicitly linking it to experience-replay in deep RL. Tse et al. (2007, *Science*, "Schemas and Memory Consolidation") shows the concrete two-timescale pattern: once a cortical schema exists, a single hippocampal-dependent exposure becomes cortex-independent within ~2 days via a compressed, schema-assisted consolidation window — i.e. new items are PROVISIONALLY fast-encoded, then folded into the slow store on a separate cycle, not updated into it immediately.

**This maps directly onto `AdditiveKGMap`'s existing two-method split, with zero new code required:**
- `fit()` (full batch SGD refit over ALL current triples) = the **cortical consolidation cycle** — slow, interleaved (every triple seen every epoch), run periodically as new generated facts accumulate.
- `compose_entity()` + `insert_entity()` (zero-training mean-of-support-edges, append a row) = the **hippocampal fast bridge** — a brand-new entity or fact gets a provisional coordinate immediately, usable for retrieval right away, WITHOUT touching the shared `X`/`D` fit for everything else, until the next `fit()` consolidation cycle folds it in properly.

Independent ML-side confirmation (this cycle's lit-scan): continual-knowledge-graph-embedding literature (arXiv:2101.05850 "Continual Learning of Knowledge Graph Embeddings"; arXiv:2512.01890 reporting EWC-style regularization cutting forgetting ~45.7% vs. naive sequential updates on KGE specifically) and generative-replay continual learning (Shin et al. 2017, NeurIPS, arXiv:1705.08690, explicitly hippocampal-replay-inspired) both confirm that naive SEQUENTIAL/online updates to an already-fit embedding model cause representation drift/interference, and that batch-flavored interleaved retraining (or replay approximating it) is the standard mitigation. **Verdict: the batch-refit / fast-bridge split is a defensible, literature-grounded design choice for the factual core's update discipline — not merely a convenient reading of an existing API.** Caveat (own honest flag, matches the lit-scan's own verdict): this is an ML-continual-learning analogy to CLS, not a claim that graph-embedding SGD literally replicates synaptic consolidation; treat as a validated engineering pattern, not a neuroscience isomorphism.

**Practical implication:** don't build an "always-online-update" ingest pipeline for the factual core. Instead: (1) new generated facts land via `insert_entity()`/`compose_entity()` immediately (retrievable same-session, matches hippocampal fast-encoding); (2) a periodic consolidation job re-runs `fit()` over the accumulated triple set (batch, interleaved, matches cortical slow learning) on a cadence tied to volume growth, not wall-clock time; (3) never let an online per-fact update touch `X`/`D` directly outside of `insert_entity`'s append-only row addition — that would be the online/sequential-interference regime the CLS + continual-KGE literature both warn against.

## 5. The linchpin build step (director's call to dispatch; not dispatched here)

**Reuse the ALREADY-VERIFIED yeast-gene ID space rather than opening a new domain.** Module #1 (Costanzo epistasis) and the verified module #2 candidate (BioGRID TAB3) both key on the IDENTICAL SGD systematic-ORF-name column (registry note section 4, scout a817f488) — this is a live, zero-crosswalk-needed canonical-ID population already in hand. Pilot the factual core against the SAME population instead of inventing a separate demo domain:

1. **Generate** a small crisp fact set (target ~50-100 facts across ~10-20 SGD systematic-ORF-ID-keyed yeast genes), restricted to the section-3 allowlist (is-a-protein-coding-gene, encodes-protein, part-of-pathway/complex, chromosome-location, GO-annotation-category) — using the exact SGD systematic name string as the entity label, not a common gene name (this is the one concrete risk flagged in the HARD-FAIL list below: LLM generation may default to a common name/alias instead of the systematic ID unless the prompt forces it).
2. **Fit** a small `AdditiveKGMap` (factual-core, own k/D) on these triples, `entity_to_idx` keyed by the SGD systematic IDs.
3. **Confirm exact identity join** against module #1's (in-flight) Costanzo map and/or module #2's BioGRID map's `entity_to_idx` — pure Python `in` check, zero crosswalk service, per the already-verified shared-ID finding.
4. **Run one 2-hop cross-tier query**: start in the core map (e.g. "gene X part-of pathway P"), confirm gene X's ID is also present in module #1's map, continue scoring in module #1's epistasis relation space for gene X. Record whether the retrieved partner/ranking is sensible (a coarse precision@k against a small known-answer holdout, not a full benchmark).
5. **Confirm independence**: refit/re-check module #1's own held-out epistasis metric with the tiny core map coexisting alongside it — should be unchanged (the "additive hub, no interference" HARD-PASS from the cross-module drill, now specifically for core<->module rather than module<->module).
6. **Run the density-audit extension (section 3)** over this tiny pilot population and report where it lands relative to the 13/3/6 floor — this is the first real data point for "how much generation effort per entity is actually required," which is currently a theory-only number.

This is a ~1-day, no-heavy-compute pilot (small triple count, no GPU needed for the core map fit) that end-to-end tests every claim in this note at once, on a population where the identity-join risk is already retired.

## Cheap decisive test (pre-registered thresholds)

**HARD-PASS** (architecture works as specified):
- (i) generated facts resolve to SGD systematic-ORF-ID strings that EXACT-match module #1/#2's existing `entity_to_idx` keys for the sampled genes, with zero manual crosswalk needed;
- (ii) the 2-hop cross-tier query (core -> identity join -> module #1) retrieves a correct/plausible target at above-chance rate using ONLY dict-membership identity equality, no learned alignment;
- (iii) module #1's own held-out epistasis metric is UNCHANGED (+/- noise floor) with the pilot core map coexisting — genuinely additive, zero cross-tier interference;
- (iv) the pilot population's density-audit numbers are directionally on-path toward the 13/3/6 floor without hitting a crispness violation (no debatable/severity-graded relation needed to reach the count).

**HARD-FAIL** (any of):
- (i) LLM-generated facts default to common/alias gene names instead of the systematic ORF ID even when explicitly prompted for it — meaning the "generation naturally reuses canonical IDs" assumption is false and a mandatory post-generation ID-resolution/crosswalk step must be added to the core pipeline (an engineering fix, not an architecture failure, but a real added cost);
- (ii) the 2-hop query cannot beat chance without a learned similarity/alignment step — meaning even core<->module composition needs more than identity-join, undermining the "cheap hub" claim generally, not just for modules;
- (iii) adding the pilot core map measurably changes module #1's performance — falsifies the "separate maps share only identity" independence claim and means the maps are not as decoupled as `AdditiveKGMap`'s per-instance design suggests;
- (iv) hitting the density floor for this pilot population requires generating causal/severity-graded facts (the reserved category in section 3) — meaning the crispness allowlist is too narrow to reach 13 attributes/entity for real domains, and either the floor number or the allowlist needs revision.

## Substrate-product implications

1. Build the factual core as a second/third standing `AdditiveKGMap` instance (or one per relation-vocabulary-family), never as a merged single graph with the conjunction modules — the modules' domain-specific bind/relation machinery stays fully separate; only the entity-ID string space is shared.
2. Do not benchmark the factual core against a frequency baseline on single-relation prediction and call a loss there a failure of the tier — that fight is structurally capped; benchmark it on canonical-ID density/coverage and on whether it measurably improves conjunction-module warm-start/constituent-feature quality instead.
3. Generation pipelines for the core MUST emit canonical-ID entity labels (not display names) as a hard prompt/pipeline constraint, and MUST restrict to the 5-category crispness allowlist (section 3), with causal/severity relations quarantined to a separately-flagged, cross-checked tier — this is the single most load-bearing lesson carried over from the epistasis LLM-gen additive-trap.
4. Build the density-audit as an EXTENSION of the not-yet-built reachability-audit tool, not a second tool — one traversal, two outputs (reachability class + attributes/modalities/exposures triple).
5. Update the ingest/generation cadence to a periodic BATCH consolidation model (`fit()` on accumulated triples) with `compose_entity()`/`insert_entity()` as the only permitted between-cycle write path — never an online per-fact SGD update into the shared `X`/`D`.
6. Pilot on the SGD-systematic-ORF-ID yeast-gene population already verified live for modules #1/#2 — this retires the identity-join risk before any new domain is opened, and produces the first real density-floor data point.
