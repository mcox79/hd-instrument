## Component-by-component

### A. OBJECTIVE / forward prediction (Q1)
- **Brain mechanism (CITED@Rao-Ballard/Friston, CITED@Rabovsky2018):** hierarchical predictive coding — a prediction is generated BEFORE new evidence arrives, from PRIOR state alone; prediction error (N400, Rabovsky) is computed at every level and drives BOTH the gate and the weight update; it is fundamentally *generative* (the model proposes what should come next).
- **Our impl (`slot_attention_wm.py:88-95`):** `surprise = 1 - cos(addr_readback, clause_rep)`, where `addr_readback` is unbound from the PRE-update slots (i.e. computed from past clauses only) and compared to the actual current `clause_rep`. Timing is right (computed before write) — this is a genuine "expectation vs. evidence" comparison, not a look-ahead cheat.
- **Faithful? PARTIAL.** The *timing* is faithful (predict-then-compare, matches Rabovsky's PE-before-update). But it is NOT a generative prediction — nothing in the network ever proposes a candidate *representation* for the next clause and is scored on how close that guess is; `addr_readback` is a retrieval/familiarity match (does what's stored resemble what's here), closer to a Hopfield energy/autoassociative signal than to hierarchical PC. And the encoder producing `clause_rep` is still the MLM-bidirectional checkpoint (ledger row 1, UNFAITHFUL) — each clause's representation is computed with full within-clause bidirectional context, so "prediction" only ever operates at clause-granularity on an already-fully-formed representation, never at the sub-clause/token level the brain's PC operates at.
- **Does it explain the result? SECONDARY, not primary.** REASONED@: a retrieval-match signal built from cosine similarity in HRR-bound space carries a lot of raw representational-similarity information that is available to an *untrained* network too (see C below) — this is a contributing factor to the random-init tie, but the objective itself is not the most direct explanation of memorize-vs-chance; the addressing/update mechanics (C) are.
- **Fix (medium priority):** a genuine generative step — before observing clause t, decode a *predicted* latent from the maintained state (e.g. `predicted = f(slots_{t-1})`) and score prediction error as `1 - cos(predicted, clause_rep_t)` rather than an unbind-and-match retrieval. This is architecturally cheap (one more small MLP) and would convert the retrieval-match into a true anticipatory PC term.

### B. BINDING — single shared content key vs. role-differentiated slots (Q2)
- **Brain mechanism (CITED@Frankland&Greene2015 PNAS, lmSTC):** MULTIPLE role-filler bindings coexist simultaneously and are role-DIFFERENTIATED (AGENT slot vs. PATIENT slot), invariant to surface position. The brain does not derive one key per sentence — it derives (at least) one key PER ROLE.
- **Our impl (`slot_attention_wm.py:66,88`):** `role_key_net(clause_rep)` — ONE learned key per clause, a function of the WHOLE clause's pooled bidirectional representation (verb + all mentioned entities blended together). This single key is used both to address (`addr_net([clause_rep, slot_summary])`) and to bind the write candidate (`bind(key, clause_rep)`).
- **Faithful? NO, and this is a shape-specific gap for MES.** A single content key must implicitly encode "which entity this clause is about" purely as a side-effect of clause-level pooling. For a MULTI-entity task (MES, by construction >1 tracked entity), two different clauses about two different entities that share syntactic form ("the X was Y") will tend to produce SIMILAR keys (verb/frame dominates the pooled representation more than the entity noun), causing key collisions — i.e., `addr_net` cannot reliably route clause t to "the slot for entity mentioned in clause t" because the key doesn't cleanly carry entity identity, only clause gist. KD (single-subject, single-entity, bridging-fact) does not stress this axis, which is consistent with KD's higher absolute performance vs. MES's chance floor.
- **Does it explain the result? YES — a strong candidate for why MES specifically (not just "any task") sits at chance.** REASONED@, P~0.45 (deflated): the multi-entity axis is exactly the one the single-shared-key design is structurally weakest on.
- **Fix (high priority, cheap):** derive the key from a smaller, more entity-focused sub-representation (e.g., the encoder's span embedding over the detected subject noun phrase, if available) rather than the full clause pool — or learn K independent key-generating heads (one per slot) so slot identity is a property of a dedicated projection, not a shared clause-level function.

### C. ADDRESSING / WORKING MEMORY — mean-pool summary + convex blend (Q3)
- **Brain mechanism (CITED@Wang2001 persistent-activity attractors; CITED@O'Reilly&Frank2006 PBWM):** PFC WM is a SET of independently-maintainable attractor states (each item/slot is its own stable pattern); the basal-ganglia gate in PBWM is evaluated PER STRIPE — each PFC stripe/slot has its OWN independent maintain-or-update decision, conditioned on that stripe's own content vs. incoming evidence. Maintenance in the brain is bistable (robust-maintain OR replace), not a graded blend.
- **Our impl (`slot_attention_wm.py:89-90,97-98,101-102`):** `slot_summary = slots.mean(dim=1)` — collapses all K slots into ONE vector, destroying per-slot identity, BEFORE `addr_net` even decides which slot to touch. `write_strength` is computed ONCE per clause (a single scalar, `gate_net` output) from `[clause_rep, addr_readback, surprise]` where `addr_readback` is ALSO an addr_w-weighted aggregate across slots — so the gate never sees any INDIVIDUAL slot's own content vs. clause match; it sees a global blend twice removed from any specific slot. The actual per-slot write amount is `addr_w[k] * write_strength` (one global scalar broadcast, modulated only by softmax weight), and the update itself is a **convex blend**: `new_slots = (1-w)*slots + w*candidate` — a graded average, not a gated replace/hold.
- **Faithful? NO — SHAPE and POSITION both wrong.** Shape: PFC WM is per-stripe/attractor, not a single mean-pooled summary; the brain's gate conditions on the SPECIFIC slot's own state, not a global average. Position: the mean-pool happens BEFORE addressing (destroying the very information addressing needs), and the gate is computed from a SECOND aggregate (`addr_readback`), so there are two lossy averaging steps between "what's actually stored per-slot" and "should this specific slot update." Metric: convex blending in HRR/cosine space accumulates crosstalk over many clause-steps (classic superposition-noise) rather than the brain's robust maintain-or-replace bistability.
- **Does it explain the result? YES — the SINGLE MOST LOAD-BEARING gap.** REASONED@, P~0.55 (deflated, novel-synthesis capped): if `addr_w` is not sharply peaked (plausible with modest logits/tanh-MLP scale, especially without an explicit sharpening/temperature term), MULTIPLE slots partially write on every clause, so slot-specific entity information smears across slots via repeated convex blending — a *training-invariant* degradation. This is exactly the signature that would (a) let train_loss reach ~0.04 (the judgment linear probe can still memorize idiosyncratic per-item slot_mean patterns even from smeared/blended slots — 64 items is easy to overfit against ANY sufficiently-high-dimensional feature vector, even a noisy one), while (b) producing NO reliable eval-time signal (the blended/crosstalk-corrupted slot_mean carries no item-general "is this entity-state consistent" structure), and (c) is present REGARDLESS of whether the encoder/WM weights are trained or randomly initialized, because the averaging/blending operations are STRUCTURAL (not learned) — directly explaining the trained-core-ties-random-init-core signature (HARD_FAIL_STRUCTURE_ALONE, the exact failure class this build was supposed to correct — see `brain_foundational_component_analysis.md` row 6 prior/design-A).
- **Fix (HIGHEST priority):** (i) make addressing per-slot-local — each slot's OWN unbound readback vs. `clause_rep` should produce that slot's OWN local match/PE scalar (no `slots.mean` step); (ii) make the write a genuine gate, not a blend — e.g. a sharper/annealed softmax (low temperature) over `addr_logits`, or a hard top-1 write with a learned soft-relaxation only early in training, so slots that are NOT addressed are truly held (not partially averaged); (iii) if convex blending must remain differentiable, at minimum push `write_strength` sharply bimodal (entropy penalty toward {0,1}) rather than leaving it a free sigmoid.

### D. KB PRIOR — persistence and protection (Q4)
- **Brain mechanism (CITED@LambonRalph2017 hub-and-spoke):** a semantic-memory prior is not a one-shot injection — the amodal ATL hub is REPEATEDLY reactivated/queried throughout comprehension, and in a Bayesian-prior reading, a well-supported prior should persistently BIAS inference, not decay after one update step.
- **Our impl (`slot_attention_wm.py:72-81`, `exp_stateful_core_situation_model_v1.py:361-378`):** `kb_prior` seeds slot 0 ONCE at `init_slots` (t=0) and is NEVER re-injected. Given the convex-blend write (C) touches slot 0 whenever `addr_w` assigns it any weight (plausible on every clause, since addressing is soft, not hard), the KB content is diluted proportional to `write_strength` on EVERY subsequent clause with no protection mechanism. Additionally, `kb_consistency` (feats line 110-113) is computed by re-reading FROM `new_slots` using the SAME clause key and rewarded via a loss term (per the cell docstring) — this creates an incentive for the network to increase `addr_w[0]` (route more attention to slot 0) for ANY clause, cheaply satisfying the auxiliary loss, rather than to use the KB content only when semantically relevant. This is a plausible reward-hacking path: capacity that should track OTHER slots (the actual maintenance signal the judgment head needs) gets diverted toward slot 0 to cheaply lower the KB-consistency loss.
- **Faithful? NO.** Both the erosion (no persistence/protection of a "world model prior" — it's an initial condition the dynamics erase, not a lasting bias) and the auxiliary-loss incentive structure (rewarding attention-to-slot-0 rather than rewarding correct USE of the prior) are unfaithful to how a semantic-memory hub is meant to function (continuously available, not consumed).
- **Does it explain the result? YES — directly explains Arm B < Arm A on KD.** REASONED@, P~0.45 (deflated): the KD result (B hurts, -0.125) is consistent with EITHER (i) the prior being washed out by convex-blend erosion before the item's decisive clause is reached (net: zero benefit + noise from an irrelevant/washed vector feeding the judge's `slot_mean` and `kb_consistency` features), or (ii) the kb_consistency loss diverting addressing capacity away from the slots that actually carry the bridging-relevant maintenance signal, net negative on the OTHER 3 judge features. Both mechanisms point at the same root cause as C (addressing/blend), i.e. C and D are coupled, not independent — fixing C (per-slot gating, sharper/protected writes) would very likely fix D as a side effect (a genuinely protected slot 0 would stop eroding and stop being a cheap sink for the auxiliary loss).
- **Fix (high priority, couples with C):** make slot 0 (or a dedicated "KB slot") EXEMPT from the standard write competition, or give it its own much smaller/learned decay rate distinct from other slots, so the prior persists and biases rather than being one more competitively-blended entry; and/or decouple `kb_consistency` from `addr_w` (score it against slot 0's OWN unbound content directly, not the addr-weighted aggregate) so the auxiliary loss cannot be gamed by shifting attention.

### E. METRIC — what the judge actually reads (Q5)
- **Brain-faithful signature (CITED@Zwaan updating-cost-at-discontinuities; CITED@Rabovsky N400-as-update):** the diagnostic quantity is the UPDATE/prediction-error trajectory, especially its value AT the discontinuity/violation point, not a static end-of-passage snapshot.
- **Our impl (verified directly, `exp_stateful_core_situation_model_v1.py:362-378`):** inside the per-clause loop, `feats` is REASSIGNED every iteration and never accumulated — after the loop, `judge_in` uses `feats["surprise"]`, `feats["write_strength"]`, `feats["addr_entropy"]` from ONLY THE LAST CLAUSE, plus `slot_mean` (final-state snapshot). The entire per-step trajectory (`per_step` list that `run_clause_stream` — the OTHER entry point in `slot_attention_wm.py` — actually returns) is computed by `wm.step` every iteration but **discarded**; `forward_item_batch` never calls `run_clause_stream` at all, it inlines its own loop and keeps only the final `feats`.
- **Faithful? PARTIAL, with one mitigating fact and one real gap.** Mitigating: IF the construction places the decisive (coherent/violated) clause LAST by design (plausible for a consistency-judgment task), then reading only the final surprise is not obviously wrong in principle — Zwaan's updating-cost is exactly "PE at the point of the discontinuity," and if that point is always the last clause, final-step surprise = discontinuity-step surprise. Real gap: `slot_mean` (the dominant, highest-dimensional judge feature) is a FINAL-STATE snapshot, so it inherits whatever crosstalk/blending (C) has already corrupted BEFORE the decisive clause is reached — the metric doesn't just fail to look at the trajectory, it is downstream of, and therefore inherits, the addressing/blend fidelity gap. Also: discarding the trajectory means the discriminator cannot access "was there a spike in surprise at clause k" (an update-cost feature explicitly named in Zwaan's paradigm) at all — only the possibly-already-decayed final value.
- **Does it explain the result? SECONDARY / compounding, not primary.** REASONED@: this is a real metric-fidelity gap but plausibly not the PRIMARY cause of the chance/tie signature — even a perfectly-faithful trajectory-based metric would still fail if the underlying slots have already collapsed to structure-alone noise (C). Worth fixing, but fixing it alone would likely not move MES off chance.
- **Fix (medium priority, do AFTER C):** have `forward_item_batch` use `wm.run_clause_stream` (already implemented, just unused) and feed the judge a trajectory-aware feature (e.g., max surprise over steps, surprise at the construction's known label-clause index) in addition to the final snapshot.

## RANKED LOAD-BEARING GAPS (2-3 most plausible causes of memorize-not-generalize + KB-hurts)

1. **C — mean-pool addressing + convex-blend write (no per-slot gating, no bistable maintain/replace).** Highest confidence (REASONED@, deflated P~0.55). Structural (not learned), so it degrades slot content identically whether the core is trained or randomly initialized — directly matches the trained-ties-random-init signature, and independently explains why a near-perfect train fit (0.04 loss, 64 easily-memorized items) coexists with zero eval generalization (the judge overfits per-item noise in a smeared feature, not a generalizable maintenance signal).
2. **B — single shared content key per clause, not role/entity-differentiated.** High confidence for WHY specifically the multi-entity MES task (not KD) sits at floor (REASONED@, P~0.45): a clause-pooled key cannot reliably disambiguate WHICH of several tracked entities a clause updates, compounding gap #1's slot-collision risk.
3. **D — KB prior with no persistence/protection + a gameable auxiliary loss.** High confidence for the KD-specific B<A result (REASONED@, P~0.45): the prior is an initial condition eroded by the same blend mechanics as #1, and the `kb_consistency` term creates an incentive to hijack addressing capacity toward slot 0 rather than to genuinely use world knowledge — net negative on the judge's other features. Coupled with #1, not independent: fixing addressing/gating plausibly fixes this too.

(Objective-fidelity (A) and metric-trajectory-discarding (E) are real, genuine gaps but rank as secondary/compounding — they would still leave the result largely unchanged if addressed in isolation without fixing C.)

## MECHANISM-limited vs. DATA-limited verdict

**MECHANISM-limited (moderate-high confidence, deflated).** The decisive tell is not merely "eval is low" (which alone is ambiguous between too-few-items and a broken mechanism) — it is the *combination* of (a) near-perfect train fit (0.042, i.e., 64 items ARE learnable by SOMETHING in this pipeline) with (b) eval performance that doesn't just underperform but exactly TIES a random-init, never-trained control. A purely data-starved-but-mechanistically-sound maintenance module would be expected to show SOME above-chance, above-random-init generalization even under-trained (partial credit scaling with data seen) — ties-exactly-to-random is the specific signature the build's own pre-registered control was designed to catch (`HARD_FAIL_STRUCTURE_ALONE`, named explicitly in the cell docstring as design-A's failure mode this build was meant to avoid), and the structural mechanism identified above (C: mean-pool + convex-blend, invariant to training) is a concrete, code-verified candidate that would PRODUCE exactly that signature. This is not proof (a genuine data-scale sweep — e.g. 64 -> 256 -> 1024 train items with the SAME mechanism — is the clean way to fully disambiguate, and was not run here), so: **can't fully rule out a compounding data contribution, but the specific tie-to-random-init result is much better explained by the named structural gap (C) than by item-count alone.**

## SINGLE HIGHEST-VALUE FIX TO TRY NEXT

**Replace the mean-pool/convex-blend addressing+write in `SlotAttentionWM.step` with per-slot-local gating:** each slot computes its OWN match (unbind THAT slot vs. clause_rep, no `slots.mean`) and its OWN write decision (sharper/near-hard gate, not a free-sigmoid blend), so addressing and gating stop discarding per-slot identity before a decision is made. This single change plausibly resolves gap #1 (the top-ranked, structural, training-invariant cause), likely improves #2 (entity collisions have less blend-noise to hide in) as a side effect, and directly reduces #3's erosion mechanism (a non-addressed slot 0 stops leaking). It is also the cheapest of the three fixes to implement and smoke (change is contained to `slot_attention_wm.py`, no new data or construction needed) — the natural next `hdi_exp_dev` cell before considering a data-scale sweep.
