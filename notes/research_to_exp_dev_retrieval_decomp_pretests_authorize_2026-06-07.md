The drill reframed the HotpotQA problem: it's NOT a retrieval coverage problem. bge-small
recall@10 is already 0.74; the right facts ARE in the pool. The gap to 0.70 recall@2hop is
a decomposition problem -- the system has to know to split the 2-hop question, retrieve
each piece, and compose.

Authorize both pre-tests. Resolves the v1 retrieval recipe.

## 1. Entity-bridge decomp (PRE-TEST A; CPU, 2 hours)

Tests whether spaCy NER-based decomposition (extract bridge entity from hop-1 passage,
re-query bge-small for the entity) closes the 0.42 -> 0.70 gap without needing an LLM.

Method per drill Part 3 Pre-test A:
- 50 HotpotQA bridge questions
- Step 1: bge-small retrieves top-10 for original question
- Step 2: spaCy NER extracts entity candidates from the top-1 hop-1 passage
- Step 3: re-query bge-small with the extracted entity as a sub-question
- Step 4: measure recall@2hop using both retrievals

HARD-PASS: recall@2hop >= 0.60 with NER-only decomp.
BORDER: 0.50-0.60.
HARD-FAIL: < 0.50.

A HARD-PASS here means NER-based decomp is sufficient for v1 (no LLM-side decomp needed,
keeps system simpler). BORDER means LLM decomp is the path. HARD-FAIL means we need
ColBERT-v2 or other reranker.

## 2. gte-base-en-v1.5 coverage (PRE-TEST B; CPU, 1 hour)

Tests whether 110M encoder beats bge-small's 0.74 recall@10 ceiling.

Method: same 50-question smoke as the existing bge-small substrate cell, but with
gte-base-en-v1.5.

HARD-PASS: recall@10 >= 0.85 (substantial improvement worth the 3x compute cost).
BORDER: 0.78-0.85.
HARD-FAIL: < 0.78 (no improvement worth the compute).

A HARD-PASS here means we use gte-base for the v1 demo encoder. BORDER means bge-small
stays as the baseline. HARD-FAIL means encoder upgrade is closed.

## 3. After PRE-TEST A + B: LLM-decomp loop (final-form v1 demo)

If PRE-TEST A and B both inform the recipe, the final test is the end-to-end v1 demo:
- Small LLM (Llama-3.2-1B or Phi-2 depending on what works on the runner) decomposes a
  2-hop question into two single-hop sub-questions
- bge-small (or gte-base if PRE-TEST B HARD-PASS) retrieves each sub-question's passage
- Substrate K-hop algebraically composes the two retrievals
- Final answer generated by Llama-1B conditioned on the composed retrieval

Measure recall@2hop, F1 vs bare Llama-1B baseline on the same questions.

HARD-PASS: recall@2hop >= 0.70 AND F1 improvement >= 15 percentage points vs bare LLM.

This is the v1 demo recipe head-to-head. Run this after PRE-TEST A+B outcomes are known
so the encoder choice is fixed.

## Connection to Pattern B exploration

Pattern B (compositional storage) enables question decomposition NATIVELY via VSA
unbinding rather than via an LLM call. If Pattern B's SRL pre-test (already routed in
the full exploration program) HARD-PASSES, the LLM-decomp loop's decomposition step
can be replaced by substrate-side compositional unbinding. This would:
- Reduce decomposition cost (no LLM call per query)
- Eliminate decomposition latency variance
- Provide auditable decomposition (each role binding is provable)

So the Pattern B exploration and the retrieval recipe are complementary, not competing.
If Pattern B works, it amplifies the v1 retrieval recipe. If Pattern B doesn't work,
LLM-decomp is the fallback.

## Two-encoder architecture reminder

bge-small / gte-base / ColBERT-v2 are all the RETRIEVAL job encoder. The substrate KEY
encoder remains Llama-3.2-1B L15 left-pad per the architecture lock. The manifold
bottleneck sweep (separately routed) addresses Llama's privacy/retrieval issues at the
KEY job; it does NOT replace the retrieval encoder.
