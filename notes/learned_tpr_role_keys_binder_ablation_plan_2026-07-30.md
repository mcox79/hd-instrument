## HEADLINE

**Build a gradient-learned TPR-style role-key module (factored role x filler, NOT a flat learned lookup) to replace oracle-averaging, then run a 3-arm binder ablation {FHRR bind/unbind, TPR tensor-product + learned unbind, mixed-selectivity conjunctive readout} on the EXISTING zero-shot-role and cross-slot-relational cells.** The literature gives real, converging, CITED support that factored/TPR structure is a genuine (not merely aspirational) fix for the flat-learned-key memorization failure the substrate already hit once (`exp_oracle_context_invariant_address_wm_v2`: even a perfect one-hot warm-started learned routing address could not generalize to a never-seen role) — Webb/Sinha/Cohen 2021 (ESBN vs LSTM/NTM, arXiv:2012.14601) and Schlag/Schmidhuber 2018 (TPR-RNN vs flat SOTA on systematic bAbI splits, arXiv:1811.12143) are head-to-head demonstrations, not analogy. But three 2023-2025 critique papers (arXiv:2405.16391 kernel theory; arXiv:2406.01012; arXiv:2412.04671) are equally clear that factored structure is **necessary-leaning, not sufficient** — a badly-trained TPR decomposition or a readout mechanism that doesn't respect the factorization can still fail to generalize. So the honest framing is: TPR gives the mechanism a *fighting chance* the flat key never had, not a guarantee. The build below is designed so a HARD-FAIL is informative either way.

## Cheap decisive test

**The decisive metric is zero-shot novel-role addressing accuracy on the SAME held-out-role split that broke the flat learned key** (`TRAIN_ROLES_V2` / `HELD_OUT_ROLES_V2`, 10/5 split already coded in `exp_oracle_context_invariant_address_wm_v2` and reused by `exp_wm_addressing_heldout_role_warmstart_v1.py` and `exp_vsa_native_bind_zeroshot_role_v1.py`). Reuse this split verbatim — do not construct a new one; the whole point is a fair, controlled A/B against a documented prior failure on the identical partition.

Cheapest possible first probe (before the full 3-arm ablation, ~1hr CPU): train the TPR role-key module alone (no binder, no downstream task) with a role-CLASSIFICATION or role-RECONSTRUCTION objective over TRAIN_ROLES_V2 only, then measure whether its induced role-key geometry (a) has higher effective rank than the oracle table's rank<=14 (measured via participation ratio / stable rank of the key matrix — cheap, no training needed once keys exist) and (b) produces a HELD_OUT_ROLES_V2 key, from a role-query probe never given a supervision label, that is closer to its true role's train-role neighbors than to a random role (a KNN/cosine sanity check, not the full task). If (a) fails (rank still <=14, same as oracle) the whole plan is moot before spending compute on the 3-arm ablation — go back to encoder-representational-capacity as the bottleneck instead of the key-derivation method.

## Falsifiable predictions (HARD-PASS / HARD-FAIL, pre-registered)

Chance floors: chance_addr = 1/15 (S_TARGET_TOTAL), chance_recall = 1/20 (V_FILL), matching the existing cells' convention.

**HARD-PASS (learned-TPR key generalizes; justifies full binder ablation + downstream build-out):**
held-out-role addressing accuracy >= 0.55 (both/all seeds) AND gap vs train-role accuracy <= 0.20 (both/all seeds) AND beats CONTROL_A (flat learned key, identical architecture minus the tensor-product factorization) by >= 0.15 absolute on held-out roles. This mirrors the exact band structure already used in `exp_wm_addressing_heldout_role_warmstart_v1.py` (HARD_PASS_HELDOUT_ROLE_GENERALIZATION), reused for continuity and because CONTROL_A's HARD_FAIL result on that cell is the direct prior to beat.

**HARD-FAIL (learned-TPR key re-memorizes exactly like the flat key; the whole learned-key direction is refuted, not just this instantiation):**
held-out-role addressing accuracy < 0.40 (any seed) OR gap > 0.35 (any seed) OR fails to beat CONTROL_A by >= 0.10 on held-out roles. Per the discipline that a miss is never a ceiling until fairly tested: a HARD-FAIL here does NOT mean "learned binding is dead" — it means THIS factorization (see Risk section) failed, and the honest next question becomes which of {factorization architecture, training objective, readout mismatch} caused it — falls to the arXiv:2405.16391 kernel-theory finding that structure-in-representation and generalization-of-the-learned-function can dissociate.

**MIDDLE-BAND (most likely outcome given the critique literature, deflated P=0.40):** held-out addressing beats CONTROL_A meaningfully (structure helps) but does not clear the HARD-PASS bar outright (e.g. 0.40-0.55 range) — meaning factorization is a real but partial fix, and the remaining gap is a readout/training-objective problem (per arXiv:2406.01012's finding that TPR decomposition extraction is often "incomplete"), not evidence against the TPR direction.

**Binder-ablation-specific HARD-FAIL (per the brain-fidelity audit's original ask, reused verbatim):** mixed-selectivity conjunctive readout beats FHRR AND TPR on zero-shot role generalization by >=0.10 absolute while being more literature-credentialed — this is the worst-case combination (picked the less-supported, lower-capability option) and would trigger a binder pivot away from FHRR as primary, independent of the role-key question.

## Build design

### 1. The learned role-key mechanism (TPR-factored, NOT a flat learned lookup)

**Architecture:** a small role-encoder MLP `f_role: R^d_enc -> R^d_role` applied to the frozen v2 encoder's role-query-extracted representation (the same fixed-role-query probe input already used by `oc.build_oracle_table` — reuse the extraction, replace only the aggregation-and-storage step). Output `d_role` is a FACTOR vector, not a lookup-table row. The key for a (role, context) pair is then formed as `key = bind_or_outer(f_role(role_query_rep), g_slot(slot_position))` — i.e., the role factor is itself composed from at least two independently-varying sub-factors (semantic-role-identity and slot-position), following Smolensky's original role x filler factorization, so that a NOVEL COMBINATION of a previously-seen role-identity-factor with a previously-seen slot-position-factor (even if the exact (role, slot) pair is new) is compositionally reachable. This is the mechanism-level answer to "why would TPR generalize where a flat key didn't": a flat learned key is one embedding row per (role) label with no internal factor structure — there is nothing to recombine, so a never-seen role has no path to a sensible vector except through incidental similarity in whatever the network happened to learn. A TPR-style key is built FROM factors that each individually get many training signals (many roles share slot-position factors; many slots share role-identity factors), so a held-out role still gets a well-trained slot-position factor and only needs its role-identity factor to land in a sensible region of the space — a strictly easier generalization problem than the flat case's "guess the whole row."

**Training objective:** joint gradient training against a RECONSTRUCTION/prediction objective, per Smolensky/McCoy (arXiv:1812.08718) and Schlag/Schmidhuber (arXiv:1811.12143) precedent — NOT a role-CLASSIFICATION cross-entropy alone (classification pressure alone reproduces the flat-lookup failure mode, since the network can shortcut with per-role logits that don't need factor structure to reduce loss). Concretely: train `f_role` and `g_slot` end-to-end through the SAME bind -> bundle -> unbind -> filler-recovery pipeline already coded in `hdlab/binding.py` and the recall-loss cells, so the loss pressure is "can you RECOVER the filler after going through the algebra," which only decreases if the factor structure is actually usable by the unbind operation — this ties the representation-learning objective to the downstream USE of the representation, closing the arXiv:2405.16391 gap (structure alone isn't sufficient; the reasoning/readout step over the structure has to actually exploit it, and training end-to-end through the real unbind forces that).

**Avoiding the flat-key failure mode explicitly:** the prior `exp_oracle_context_invariant_address_wm_v2` HARD-FAIL was a per-role lookup table (perfect one-hot warm start) that had no compositional path to a never-seen role at all — structurally, it could not have generalized regardless of training regime, because there was no factor to recombine. The TPR design here is different in kind, not degree: every role's key is COMPUTED from sub-factors shared with other roles, so held-out generalization is a claim about factor-space smoothness (testable, per the cheap KNN check above) rather than a claim about table lookup extrapolation (which the field has already shown does not happen). This is the crux distinction the prompt asked to address explicitly, and it is the one place this plan is making a REASONED (not fully CITED) bridge — the cited papers show TPR/factored structure beating flat baselines on THEIR tasks (bAbI systematic splits, SCAN-style benchmarks, novel-entity binding); no cited paper is this exact substrate's role/slot construction, so treat the specific magnitude of the effect here as unverified until the cheap KNN probe and the full cell run.

**Why this is not the forbidden bolt-on reader:** the forbidden pattern (per `[[feedback_no_bolt_on_existing_reader_earn_comprehension_own_mechanism_2026-07-27]]`) is supplying an EXTERNAL reading/parsing MECHANISM that does the comprehension work FOR the substrate (e.g. a pretrained parser's output standing in for learned syntax). This design is different: `f_role`/`g_slot` are small, freshly-initialized, gradient-trained-FROM-SCRATCH modules that learn role representations using the substrate's OWN frozen encoder reps as input and the substrate's OWN bind/unbind algebra as the training signal. No external model's parse, embedding, or role-label ever enters the computation graph at inference time — the only thing "supplied" is architecture (a factorization prior) and objective (reconstruct-through-the-algebra), which is knowledge/data-adjacent scaffolding, not a borrowed reading mechanism. This is the same category the SUBSTRATE_CHARTER treats as acceptable (supplying structure/knowledge) vs forbidden (supplying the mechanism itself).

### 2. The binder ablation (3 arms, matched)

Reuse `exp_vsa_native_bind_zeroshot_role_v1.py` and `exp_cross_slot_relational_binding_v1/v2.py` as the task harness (do not build new tasks — the brain-fidelity audit's own cheap-decisive-test already specified this).

- **Arm A (FHRR, current):** `hdlab/binding.py` `bind`/`unbind` (elementwise complex multiply / conjugate multiply), keys = the new learned-TPR keys (Section 1) instead of oracle-averaged.
- **Arm B (TPR tensor-product):** literal outer-product bind (`role (x) filler`, flattened/truncated to d via a fixed random projection or the low-rank TPR factorization itself) + learned linear unbind (a small trained readout, not algebraic conjugate-multiply — TPR's native inverse when the outer product isn't literally stored at full rank).
- **Arm C (mixed-selectivity conjunctive control, reused from the brain-fidelity audit's own Arm 2 spec):** elementwise product of role and filler passed through a FIXED random nonlinear expansion (Rigotti/Fusi mixed-selectivity population-code style), linear-readout decode instead of algebraic unbind.

All three arms use the IDENTICAL learned-TPR role keys from Section 1 (the role-key question and the binder question are separable — ablate one variable at a time). Measure, per arm: held-out-role zero-shot addressing/recall accuracy (primary), capacity-before-crosstalk (number of simultaneously superposed bindings before floor-level degradation, reusing the existing superposition/bundle harness), and wall-clock/FLOP cost (FHRR's O(N log N) FFT vs TPR's O(N^2) outer product vs mixed-selectivity's expansion width — this determines the engineering tiebreak if generalization ties, per the brain-fidelity audit's own MIDDLE-BAND resolution rule).

### 3. Fair-test design

- Reuse the EXACT TRAIN_ROLES_V2/HELD_OUT_ROLES_V2 10/5 split, same seeds {7,13,19}, same frozen v2 encoder checkpoint, same SLOT_NOUNS/COLORS/EVENT_TEMPLATES construction as the existing cells — no new confound introduced.
- CONTROL_A (can-fail floor #1): flat learned key (embedding table per role, no factorization), identical training budget and downstream architecture — MUST reproduce the prior `exp_oracle_context_invariant_address_wm_v2` near-chance held-out result, else the split/construction has drifted and the whole comparison is INVALID (same discipline as `CONTROL_A_NO_WARMSTART` in `exp_wm_addressing_heldout_role_warmstart_v1.py`).
- CONTROL_B (can-fail floor #2, per-role-lookup ceiling): oracle-averaged keys (the ORIGINAL non-fidelity construction), included ONLY as an upper-bound-probe reference captioned as such, never as a comparison target for "which is better" — its role is purely to show what train-role-only performance looks like when address supervision is perfect, so a held-out gap is legible.
- Floor batteries (ctx_fails / wrong_fails / shuf_fails) reused verbatim from the existing cells' floor-validity pattern — all must fail as expected or the run is INVALID, not a genuine positive.
- Genuine novelty requirement: HELD_OUT_ROLES_V2 labels never appear in ANY training signal (role-key training, aux loss, warm-start supervision) for any arm — asserted at runtime exactly as `exp_wm_addressing_heldout_role_warmstart_v1.py` already does (`INTEGRITY VIOLATION` assertion pattern, reuse verbatim).

### 4. Honest risk

The single biggest risk, named directly: **the TPR role-encoder could still collapse into a de-facto flat lookup if its factor sub-spaces end up perfectly role-identity-correlated** (i.e., if `f_role(role_query_rep)` learns a representation where each role's factor is orthogonal to every other role's factor with no shared structure across roles — functionally a one-hot embedding wearing a tensor-product costume). This is exactly the failure the arXiv:2406.01012 critique paper describes ("decomposition to structural representations was incomplete") and the arXiv:2405.16391 kernel-theory paper predicts is possible even with nominally factored architecture. **What would refute the whole learned-key direction:** if, even after this design, held-out addressing stays at CONTROL_A's near-chance level (HARD-FAIL band above) AND the cheap effective-rank probe shows the learned key matrix's rank collapsed back toward the oracle table's rank<=14 ceiling — that combination would mean the substrate's current encoder representations themselves don't carry enough independently-varying role-identity signal for ANY key-derivation method (oracle-averaged, flat-learned, or TPR-factored) to produce a well-conditioned, generalizing key, and the bottleneck is upstream in the encoder's representational geometry, not in how keys are derived from it. That would be a genuinely informative negative — it would redirect effort to encoder representational capacity (a bigger, harder pivot) rather than continuing to iterate on key-derivation methods.

P_deflated for "learned-TPR role keys clear the HARD-PASS band on this substrate's specific construction": **0.40** (lit-scan calibration penalty applied; the cited evidence for claim (1) is real and head-to-head on comparable tasks, but no cited paper is this exact role/slot construction, and the critique literature's necessary-but-not-sufficient finding is itself well-cited, so this stays below the 0.50 novel-synthesis cap with room for the honest MIDDLE-BAND being more likely than the clean HARD-PASS).

### 5. Sequencing vs the in-flight syntactic-role encoder diagnostic

The in-flight diagnostic (whether the frozen encoder encodes syntax->role at all) is a PREREQUISITE check, not a parallel-track item, for exactly the reason named in the Risk section: if the encoder does not carry independently-varying role-identity signal, no key-derivation method downstream can fix that, and this whole build would be diagnosing a key-derivation problem that is actually an encoder-representational problem. Recommended sequencing: (a) if the syntactic-role diagnostic is cheap and near-complete, let it finish first and read its result before committing full compute to the TPR build — a negative result there changes this plan's priority ordering (encoder fix would need to come first). (b) If it is not near-complete or is expensive to wait on, the cheap effective-rank / KNN probe in this plan's "Cheap decisive test" section is a strictly cheaper, narrower proxy for the same upstream question (does the encoder's role-query rep carry recoverable role-identity structure) and can run in parallel without waiting — treat its result as a fast partial answer, with the full syntactic diagnostic as the authoritative follow-up regardless of which finishes first.

## Substrate-product implications

This is a sequencing/priority signal, not a publication angle. If HARD-PASS: the substrate gains its first non-oracle, non-flat-lookup, genuinely generalizing role-key mechanism — removing the least-defensible component in the brain-fidelity audit AND unblocking a fair (non-confounded) binder ablation, since any FHRR-vs-rival comparison run on oracle keys today is confounded by the oracle key's own known rank-deficiency (this note's Section on the phase-conversion NO_LIFT). If MIDDLE-BAND: factorization is a real partial fix; next move is isolating whether the gap is in the training objective (per arXiv:2406.01012, try a harder joint end-to-end objective before abandoning TPR) or the readout. If HARD-FAIL with rank-collapse: redirect to encoder representational capacity as the true bottleneck, which is a materially bigger and more expensive pivot — worth knowing NOW via the cheap probe before committing the full 3-arm ablation's compute budget.
